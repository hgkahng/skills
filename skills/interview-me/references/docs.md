# Interview: docs

Goal: learn how the user wants documentation structured and pitched so agents
write docs the user would keep rather than rewrite.

## Look first
Existing README, docs folder, changelog, comment style. Note what already
exists and ask only where it's unclear whether it's the standard to follow.

## Topics (pick what matters; don't ask all)

- **Good and bad examples** — "Which docs (any project) do you love reading? Which do you hate?" Start here.
- **Past annoyances** — "What do generated docs get wrong?" (too long, restating code, stale tone…)
- **Reader** — new user, teammate, future you? Expertise level? What should they be able to do after reading?
- **Doc types** — which matter here: README, how-to, reference, design decision, runbook, changelog?
- **Structure** — example-first or explanation-first? Quickstart at the top? Headings vs flowing text?
- **Depth** — how much "why" vs "how"? Document obvious things or only surprises?
- **Length** — one-screen README, or thorough?
- **Code samples & diagrams** — runnable examples required? Diagrams welcome, and in what format?
- **Tone** — formal, friendly, terse?
- **Upkeep** — where docs live, and should the agent update docs whenever it changes behavior?

## Good entries look like
- **README: one-line purpose, then a working quickstart, then details** — why: readers decide in 10 seconds.
- **Update docs in the same change that alters behavior** — why: stale docs are worse than none.
