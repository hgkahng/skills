Idempotent means that doing something many times has the same effect as doing it once.

A light switch labeled "turn on" is a good example. Press it once and the light is on. Press it five more times and the light is still on. A switch that toggles is not idempotent, because each press changes the result.

In an API, an operation is idempotent if sending the same request twice leaves the system in the same state as sending it once. The reply might differ, but the data on the server ends up the same.

Here are some examples:

- "Set the user's email to a@example.com" is idempotent. Run it ten times and the email is still a@example.com.
- "Delete order 42" is idempotent. After the first call the order is gone. Later calls change nothing more.
- "Add $10 to the account" is not idempotent. Each call adds another $10.
- "Create a new order" is usually not idempotent. Each call makes another order.

People care because networks fail. Say your app sends a payment request and the connection drops before the reply arrives. You don't know if the server got the request. You have two choices. You can retry and risk charging the customer twice. Or you can not retry and risk never charging them.

If the operation is idempotent, you can just retry. The worst case is that it runs twice with no extra harm. That makes retries safe, which makes your system much simpler and more reliable.

In HTTP, GET, PUT, and DELETE are meant to be idempotent. POST is not. For operations like payments, which are usually POST, many APIs let you send an "idempotency key." This is a unique ID you attach to the request. If the server sees the same ID again, it doesn't repeat the work. It returns the result from the first time.
