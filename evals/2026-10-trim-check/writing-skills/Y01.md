Idempotent means that doing something many times has the same effect as doing it once.

A light switch marked "On" is a good example. Press it once and the light is on. Press it five more times and the light is still on. A switch that flips the light each time you press it is not idempotent.

People care about this in APIs because requests can fail in messy ways. Say your app sends a request and the connection drops before a reply comes back. You don't know if the server got the request. The safe move is to send it again. But that is only safe if repeating the request does no extra harm.

Here is how that plays out:

- **Safe to repeat:** "Set the user's email to a@example.com." Do it twice and the email is the same. Deleting an item by its ID also works this way. Once it's gone, a second delete changes nothing.
- **Not safe to repeat:** "Charge this card $50." Do it twice and the customer pays $100.

In HTTP, the methods GET, PUT, and DELETE are meant to be idempotent. POST usually is not.

When an action isn't naturally idempotent, APIs often add an idempotency key. This is a unique ID that the client sends with the request. If the server sees the same ID again, it skips the work and returns the first result. That way a retry can never charge a card twice.
