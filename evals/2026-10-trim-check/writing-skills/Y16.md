# Hunting a Memory Leak in a Node.js Service: Full Walkthrough

The method is: confirm the leak, reproduce it, take heap snapshots at different times, compare them, find what is holding the memory, fix it, and verify the fix.

## Step 0: Know the vocabulary

- **Heap**: the memory V8 uses for your JavaScript objects. Most leaks live here.
- **RSS (resident set size)**: the total memory the OS has given the process. It includes the heap plus Buffers, native addons, and the runtime itself.
- **Garbage collection (GC)**: V8 frees objects that nothing can reach any more. A **leak** is memory that is still reachable, so GC can't free it, but that your program no longer needs.
- **Retainer**: the chain of references that keeps an object alive. Finding the retainer is the whole job.

Growth is not automatically a leak. V8 grows the heap lazily and frees it in bursts, so a sawtooth pattern (rises, then drops) is normal. A leak is a **floor that keeps climbing**: the low points after each GC get higher over time.

## Step 1: Confirm there is a leak

1. Graph memory over hours or days from your monitoring, or log it yourself:

   ```js
   setInterval(() => {
     const m = process.memoryUsage();
     console.log(JSON.stringify({
       rss: m.rss, heapUsed: m.heapUsed, heapTotal: m.heapTotal,
       external: m.external, arrayBuffers: m.arrayBuffers,
     }));
   }, 30_000).unref();
   ```

2. Read the numbers to decide where to look:
   - **`heapUsed` climbing**: JavaScript objects are leaking. Continue with the heap snapshot steps below.
   - **`rss` climbing but `heapUsed` flat**: the leak is outside the JS heap. Check `external` and `arrayBuffers` (Buffers, streams), native addons, or memory fragmentation. Heap snapshots won't show it directly.
   - **`external` or `arrayBuffers` climbing**: Buffers are being retained, often by unclosed streams or by caches of large payloads.
3. Check whether the process is simply hitting its memory limit. Node's default old-space limit depends on version and system memory. In containers it is often lower than you expect. If the process is OOM-killed, you will see `JavaScript heap out of memory` in the logs (V8 limit) or an exit code 137 (the OS or container killed it).

## Step 2: Make it reproducible

Leaks are far easier to find when you can trigger them on demand.

1. Run the service locally or in staging with production-like config.
2. Find the traffic that grows memory. Replay real requests or use a load tool such as `autocannon`, `k6`, or `wrk`:

   ```bash
   npx autocannon -c 20 -d 120 http://localhost:3000/suspect-endpoint
   ```

3. Test one endpoint or job at a time. When memory stops growing with one of them idle, you have narrowed the search.
4. Expose GC so you can force it during tests:

   ```bash
   node --expose-gc server.js
   ```

   Then call `global.gc()` before measuring. Memory that survives a forced GC is retained.

## Step 3: Capture heap snapshots

A heap snapshot is a full dump of every object on the heap and what references it. The technique is to take **several snapshots at different points** and look at what grew between them.

### Option A: Chrome DevTools (easiest locally)

1. Start the service with the inspector:

   ```bash
   node --inspect server.js
   ```

2. Open `chrome://inspect` in Chrome, click **inspect** under your Node target, and go to the **Memory** tab.
3. Choose **Heap snapshot** and click **Take snapshot**.

### Option B: Write snapshots from code (best for staging or production)

```js
const v8 = require('node:v8');
// Writes a .heapsnapshot file to the current directory and returns its name.
const file = v8.writeHeapSnapshot();
console.log('wrote', file);
```

Trigger this from a protected admin route or on a signal:

```js
process.on('SIGUSR2', () => console.log('snapshot:', require('node:v8').writeHeapSnapshot()));
```

You can also start Node with `--heapsnapshot-signal=SIGUSR2` and send the signal with `kill -USR2 <pid>`.

Warnings before you do this on a live service:
- Taking a snapshot **pauses the process** and needs memory of roughly the heap size or more. On a nearly full heap it can crash the process. Do it on one instance that is out of the load balancer if you can.
- Snapshots contain your data (tokens, user content). Treat the files as sensitive.

### Option C: Capture at the moment of failure

```bash
node --heapsnapshot-near-heap-limit=2 server.js
```

This writes snapshots as the heap approaches its limit. It is useful when the leak is slow and you can't watch it.

## Step 4: The three-snapshot technique

This is the standard way to separate leaked objects from normal working memory.

1. Start the service and **warm it up**: send some traffic so caches, connection pools, and lazy-loaded modules are initialized. Their one-time cost isn't the leak.
2. Force a GC, then take **Snapshot 1** (baseline).
3. Send a batch of the suspect traffic, such as 1,000 requests.
4. Force a GC, then take **Snapshot 2**.
5. Send **exactly the same batch** again.
6. Force a GC, then take **Snapshot 3**.

Anything that appears in snapshot 3 but wasn't in snapshot 2, in proportion to the traffic you sent, is a leak candidate. Objects that appeared once during warm-up and stayed constant are not.

## Step 5: Read the snapshots in DevTools

Load the snapshots in the **Memory** tab (or via the **Load** button for files).

1. Select Snapshot 3 and change the dropdown from **Summary** to **Comparison**. Compare against Snapshot 2.
2. Sort by **# Delta** (objects added) or **Size Delta**. The classes at the top that grow in step with your request count are suspects. The columns:
   - **Shallow size**: memory held by the object itself.
   - **Retained size**: memory that would be freed if this object were collected. A tiny object with a huge retained size is often the root of the problem.
3. Look for suspicious constructors. Typical culprits:
   - `(string)`, `(array)`, `(closure)`, `Object`, `Map`, `Set`: generic, so click into them and look at the individual instances.
   - Your own classes, such as `Session`, `RequestContext`, or `Connection`, whose count equals the number of requests you have sent.
   - `Buffer` or `ArrayBuffer`.
   - `Promise` or `Timeout`/`Timer` objects piling up.
4. Click one leaked instance. The **Retainers** panel at the bottom shows the reference chain from a GC root to that object. Read it from the bottom up: the last entry is what's holding on. Common endings:
   - A **module-level variable** (a `const cache = new Map()` or an array at file scope).
   - A **closure** (`context` in a function scope) captured by a long-lived callback.
   - An **EventEmitter listener** array.
   - A **timer** (`Timeout` in `(Timers)` or the timers list).
5. Distinguish "detached" or "leaked" objects from legitimate ones. Ask of each: should this still exist after the request finished?

## Step 6: Match the pattern to the cause

Most Node.js leaks fall into a few categories. Use the retainer chain to identify yours.

### 1. Unbounded caches and collections

A module-level `Map`, object, or array that only ever gets added to.

```js
const cache = {};
app.get('/user/:id', async (req, res) => {
  cache[req.params.id] = await loadUser(req.params.id); // never evicted
  res.json(cache[req.params.id]);
});
```

Fix: bound the cache with a size limit and TTL (for example an LRU such as `lru-cache`), or use an external cache like Redis.

### 2. Event listeners added repeatedly

```js
app.get('/stream', (req, res) => {
  eventBus.on('update', data => res.write(data)); // added on every request, never removed
});
```

Node warns `MaxListenersExceededWarning: Possible EventEmitter memory leak detected`. Treat that warning as real, not noise. Fix by removing the listener when the request ends:

```js
const handler = data => res.write(data);
eventBus.on('update', handler);
req.on('close', () => eventBus.off('update', handler));
```

### 3. Timers and intervals never cleared

```js
setInterval(() => poll(session), 1000); // keeps `session` alive forever
```

Fix: store the handle and `clearInterval` it when the owner is done. Use `.unref()` if the timer shouldn't keep the process alive.

### 4. Closures capturing more than you meant

A long-lived callback that closes over a large object keeps all of it alive, even if it uses one field. Pull out only the value you need before creating the closure, or set big references to `null` when finished.

### 5. Global state and request data stored globally

Attaching per-request data to a global, a singleton, or a module-level structure keyed by something that is never cleaned up (request IDs, socket IDs, user IDs). Use `WeakMap`/`WeakRef` for data tied to an object's lifetime, so it is freed when that object is.

### 6. Unclosed resources

Streams, sockets, database cursors, file handles, and HTTP agents not closed on error paths. Use `stream.pipeline()` (which handles cleanup), `try/finally`, and make sure error paths release resources too.

### 7. Promises that never settle

A promise that never resolves or rejects keeps its closure alive. This is common with missing timeouts on outbound calls. Add timeouts (`AbortSignal.timeout(ms)`) and handle every path.

### 8. Third-party libraries

Logging, metrics, tracing, or APM libraries that accumulate labels or entries. A classic case is a metrics library given an unbounded label such as a user ID or full URL, which creates a new time series per value. Check the retainer chain for library names under `node_modules`.

### 9. Memory outside the JS heap

If `heapUsed` is flat while RSS grows, look at native addons, Buffers (`external`/`arrayBuffers`), and allocator fragmentation. Tools like `--max-old-space-size` won't help. Try `jemalloc` as the allocator, update native modules, or profile with `valgrind`/`heaptrack` if you suspect native code.

## Step 7: Complementary tools

- **Allocation timeline** (DevTools Memory tab, "Allocation instrumentation on timeline"): record while you send traffic. Blue bars that never turn gray are objects allocated and never freed. Click a bar to see what was allocated and the code location.
- **Allocation sampling** ("Allocation sampling"): low overhead, shows which functions allocate the most memory that is still live. It is suitable for a production-like setting.
- **`clinic.js`** (`npx clinic doctor -- node server.js`, then `clinic heapprofiler`): automated diagnosis and flame-graph-style views of allocations.
- **`memlab`** (from Meta): automates the snapshot-compare process and reports leak traces.
- **`--trace-gc`**: prints each garbage collection with before and after sizes, so you can watch whether the retained size keeps rising.
- **`process.report`** and `--report-on-fatalerror`: diagnostic reports that include memory stats at the time of failure.

## Step 8: Fix it, then verify

1. Make the smallest change that addresses the retainer chain you found.
2. Repeat the exact reproduction from Step 2 and the three-snapshot comparison from Step 4. The delta for your suspect class should drop to near zero.
3. Run a **longer soak test** (an hour or more at steady load) and watch the post-GC floor of `heapUsed` stay flat. Short tests can miss slow leaks.
4. Deploy to one instance first (canary) and compare its memory graph with the others for a day.
5. Add a guard so this doesn't return:
   - Alert on the post-GC heap floor rising, not on raw usage.
   - Add a test that makes N requests, forces GC, and asserts the count of instances of your key class stays bounded.
   - Keep the `MaxListenersExceededWarning` visible in logs.

## Quick checklist

1. Plot `heapUsed`, `rss`, `external`: which one climbs?
2. Reproduce with a load tool against a single endpoint.
3. Warm up, GC, snapshot; traffic, GC, snapshot; same traffic, GC, snapshot.
4. Compare snapshots 3 vs 2, sort by delta.
5. Click a leaked instance and read its Retainers chain.
6. Match to a cause: cache, listener, timer, closure, global, unclosed resource, never-settling promise, library.
7. Fix, repeat the same measurement, and soak test.
8. Add monitoring so you catch regressions early.

## A note on emergency mitigation

While you investigate, you can reduce the pain by restarting instances on a schedule or at a memory threshold, or by raising the limit with `--max-old-space-size=<MB>`. These don't fix anything. They buy time, and they can hide the leak from you, so keep one instance running unmodified when you need to observe it.
