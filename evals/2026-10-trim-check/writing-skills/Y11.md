# Hunting a memory leak in a Node.js service

A memory leak is memory your program keeps reachable after it no longer needs it, so the garbage collector (GC) cannot free it. The hunt has five phases: confirm it is a leak, reproduce it, capture evidence, find the retaining code, and verify the fix.

## Key terms

- **Heap**: memory for JavaScript objects, managed by V8's GC. Most leaks live here.
- **RSS (resident set size)**: total memory the OS has given the process. It includes the heap, native buffers, code and more.
- **Retainer**: the chain of references that keeps an object alive. Finding the retainer is the whole job. Objects are never "leaked" on their own. Something still points at them.
- **Shallow size**: memory held by the object itself.
- **Retained size**: memory that would be freed if the object were collected, including everything only it keeps alive.
- **Heap snapshot**: a dump of every object on the heap and the references between them.

## Step 1: Confirm it is a leak and not normal behavior

Memory that rises is not automatically a leak. V8 grows the heap lazily and collects in bursts, so a healthy service shows a sawtooth pattern.

1. Chart memory over hours, not minutes. Use your metrics system, or log `process.memoryUsage()` periodically:

```js
setInterval(() => {
  const m = process.memoryUsage();
  console.log(JSON.stringify({
    rss: m.rss,
    heapUsed: m.heapUsed,
    heapTotal: m.heapTotal,
    external: m.external,
    arrayBuffers: m.arrayBuffers,
  }));
}, 30_000).unref();
```

2. Read the pattern:
   - **Sawtooth with a flat floor** (the low points stay level): healthy.
   - **Sawtooth where the low points keep climbing**: a leak. Look at the troughs after GC, not the peaks.
   - **Steady climb that tracks traffic**: a leak tied to requests.
   - **Climb that happens with no traffic**: a leak in a timer, a background job or a subscription.
   - **Step up then flat**: usually a cache warming up or a one-time load, not a leak.

3. Work out which kind of memory is growing:
   - `heapUsed` rising: a JavaScript object leak. Continue with this guide.
   - `rss` rising while `heapUsed` stays flat: a native or off-heap leak. Look at `external` and `arrayBuffers` (Buffers, streams not closed, native addons, compression or image libraries). Heap snapshots will not show the cause directly. Check for unclosed streams and sockets, and for native modules.
   - Both flat but the container is killed: your container limit is below what Node wants to use. Check `--max-old-space-size` against the container limit (set it to roughly 75 to 80 percent of the limit).

4. If it is production, note what the growth rate is per hour and per request. You will use this number to check your reproduction and your fix.

## Step 2: Reproduce it somewhere you can poke at it

Debugging in production is possible but slow and risky. Prefer a local or staging reproduction.

1. Run the service with the same Node version and the same dependencies as production.
2. Generate load that resembles production. Tools: `autocannon`, `k6`, `wrk`, or a script that replays real requests.
3. Pin down which endpoint or job causes growth. Hit one endpoint at a time and watch `heapUsed` after forcing GC (next step). The endpoint whose floor rises is your suspect.
4. Start Node with GC exposed so you can force collection and read clean numbers:

```bash
node --expose-gc --inspect server.js
```

```js
global.gc();
console.log(process.memoryUsage().heapUsed);
```

Forcing GC before measuring removes the noise of garbage that is simply not collected yet. If `heapUsed` still climbs after a forced GC and repeated identical load, you have a leak.

## Step 3: Capture heap snapshots (the three-snapshot technique)

The most reliable method is to compare snapshots taken at different points and look only at what grew.

1. Start the service with the inspector: `node --inspect server.js`.
2. Open Chrome and go to `chrome://inspect`, then click **inspect** under your Node target. (You can also use VS Code's debugger or `node --inspect-brk`.) Open the **Memory** tab.
3. Warm up first. Send some traffic so lazy initialization, caches, connection pools and JIT work have settled. Otherwise your diff is full of one-time allocations.
4. Take **Snapshot 1** (select "Heap snapshot", then "Take snapshot"). Taking a snapshot forces a GC first.
5. Send a fixed batch of the suspect traffic, for example 1,000 requests.
6. Take **Snapshot 2**.
7. Send the same batch again.
8. Take **Snapshot 3**.

Why three: allocations in snapshot 2 can be one-time warmup. Anything that grows again between snapshots 2 and 3 by a similar amount is growing per batch, which is the signature of a leak.

### Reading the diff

1. Select Snapshot 3. In the view dropdown choose **Comparison**, and compare against Snapshot 2 (or select "Objects allocated between Snapshot 1 and Snapshot 2" in the Summary view for a similar effect).
2. Sort by **# Delta** (count) or **Size Delta**.
3. Look for constructors whose delta is close to the number of requests you sent (for example +1000 `Object`, `Closure`, `Promise`, `string`, or one of your own class names). A count that scales with your batch size points at per-request retention.
4. Ignore noise: `(compiled code)`, `(system)`, and small deltas.
5. Click a suspicious row, then click one instance. The **Retainers** panel at the bottom shows the reference chain back to a GC root. Read it from the bottom (the root) upward to the object. The place where your own code appears is where the leak lives. Typical retainers:
   - a `Map`, `Set`, array or plain object at module scope
   - a closure's context (shown as `context` in the chain)
   - an `EventEmitter`'s `_events` listener list
   - a timer or interval object
   - a `Promise` that never resolves

6. Use the **Distance** column. Objects at small distance from the root are usually held by long-lived globals. Large distance means a long chain, so follow it.

### Alternative: allocation profiling

If the diff is unclear, use **Allocation instrumentation on timeline**:

1. Start recording, run your traffic, stop.
2. Blue bars are allocations that are still alive at the end. Gray bars were freed.
3. Select a stretch of persistent blue bars and the constructors panel lists what was allocated and never freed, with the allocation stack for each. This ties objects directly to the code that created them. It slows the process down a lot, so use it locally.

For a lighter option, **Allocation sampling** gives approximate allocation sites with low overhead and is safe on a staging box.

## Step 4: Capture snapshots from a service you cannot attach to

If you can only reach the process remotely:

1. Write a snapshot from inside the process with the built-in API:

```js
const v8 = require('node:v8');
const file = v8.writeHeapSnapshot(); // returns the filename
```

2. Or start Node with a signal trigger:

```bash
node --heapsnapshot-signal=SIGUSR2 server.js
# then:  kill -USR2 <pid>
```

3. Or have Node dump one right before it dies from out-of-memory:

```bash
node --heapsnapshot-near-heap-limit=3 server.js
```

4. Copy the `.heapsnapshot` files to your machine and load them in Chrome DevTools (Memory tab, "Load").

Three warnings before doing this on a live process:

- **Writing a snapshot blocks the event loop** and needs memory roughly equal to the heap size, often more. On a large heap it can freeze the service for many seconds and can push a near-limit process over the edge. Take it from one instance that has been removed from the load balancer.
- **Snapshots contain your data**: request bodies, tokens, user information, secrets. Treat the files as sensitive and do not share them casually.
- Take at least two, spaced apart in time, so you can compare.

Other tools worth knowing: `clinic.js` (`clinic doctor` and `clinic heapprofiler`), `memlab` (automates leak finding in a scripted scenario), and APM products with continuous profiling.

## Step 5: Recognize the usual culprits

Once you know what object type is growing and who retains it, match it against these common causes.

**1. Unbounded caches and module-level collections**

```js
const cache = {};
app.get('/user/:id', async (req, res) => {
  cache[req.params.id] = await load(req.params.id); // grows forever
});
```

Fix: bound the cache with an LRU (`lru-cache`) with a max size and TTL.

**2. Event listeners added repeatedly and never removed**

```js
app.get('/x', (req, res) => {
  emitter.on('update', () => res.write('...')); // one listener per request
});
```

Node warns "MaxListenersExceededWarning: Possible EventEmitter memory leak detected". Never silence that warning with `setMaxListeners` without understanding it. Fix: `emitter.off(...)` or `once(...)`, and remove listeners when the request or socket closes.

**3. Timers and intervals that are never cleared**

A `setInterval` keeps its callback and everything the callback closes over alive. Clear it with `clearInterval` when its owner is done.

**4. Closures capturing more than you think**

A closure keeps alive everything in its scope that any sibling closure uses. A small callback can pin a large buffer or request object. Fix: null out large references when done, or restructure so the long-lived callback does not share a scope with big data.

**5. Promises and async work that never settle**

Pending promises, queues that only grow, and retries without a limit hold their closures forever. Check for missing timeouts and missing `AbortController` use on outbound calls.

**6. Request-scoped data stored globally**

Storing `req`, `res`, sockets or sessions in a global `Map` keyed by ID and never deleting on disconnect. Fix: delete on `close` and `error` events.

**7. Streams not consumed or closed**

A stream that errors or is abandoned without `destroy()` keeps buffers and file descriptors. Use `stream.pipeline` (it cleans up on error) instead of manual `.pipe()`.

**8. Unbounded metrics or log labels**

Metrics libraries that create a new time series per unique label value (user ID, URL with an ID in it) grow forever. Keep label cardinality low.

**9. Third-party libraries**

Check the library's issue tracker for your version. Upgrade, or isolate by removing it from the reproduction.

**10. Global state in tests or hot reload**

Only affects dev environments, but worth ruling out if the leak appears only locally.

## Step 6: Prove the cause before you fix it

1. Form a specific claim: "`sessionStore` holds one entry per request and never deletes."
2. Test it: log the collection size (`sessionStore.size`) under load. It should climb in step with traffic.
3. Apply a minimal fix, or comment out the suspect code path, and run the same load again.

## Step 7: Verify the fix

1. Re-run the same reproduction with the same load, for long enough that the old leak would have clearly shown (at least several times the earlier growth window).
2. Force GC and compare the floor of `heapUsed`. It should stay flat.
3. Take a fresh three-snapshot comparison. The constructor that grew should no longer show a delta proportional to requests.
4. Deploy to one production instance first (canary) and watch the post-GC memory trend for a full traffic cycle (usually a day). Compare with the growth rate you recorded in Step 1.
5. Add a regression guard: an alert on the post-GC heap floor trend, a load test in CI that asserts bounded heap growth, or `memlab` scenarios.

## Step 8: Reduce the cost of future leaks

- Always set `--max-old-space-size` explicitly and below your container limit, so Node fails with a clear heap error and a snapshot rather than being silently killed by the OS.
- Enable `--heapsnapshot-near-heap-limit` in staging.
- Export `process.memoryUsage()` and GC metrics (for example with `prom-client`'s default metrics) so you can see the floor trend on a dashboard.
- Put a size limit on every cache, queue, map and buffer you add.
- Restarting the process on a schedule can buy time, but it hides the leak and does not fix it.

## Quick checklist

1. Chart heap after GC over hours. Is the floor rising?
2. Is it `heapUsed` (JS objects) or `rss` and `external` (native)?
3. Reproduce locally with load and `--expose-gc`.
4. Warm up, then take snapshots 1, 2 and 3 around identical batches of traffic.
5. Compare snapshots 2 and 3 and sort by delta. Find a count that matches your request count.
6. Read the retainer chain to your own code.
7. Fix it, then re-run the same load and confirm a flat floor.
8. Canary in production and add a guard so it cannot come back silently.
