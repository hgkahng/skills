**Short answer: not ready.** A 4-point gap from one seed each, with an asymmetric tuning budget, doesn't yet support the claim "my variant beats LoRA." The good news is that your budget covers every fix below with room to spare.

## Fatal

**1. Unequal tuning.** Your method got 6 learning rates and standard LoRA got the default. LoRA is sensitive to learning rate, and the default is rarely the best value for a given model and dataset. A 4-point gap is well within what a tuned LoRA baseline can recover. Right now the result could mean "my variant is better" or "I tuned one arm and not the other," and you can't tell which.

*Fix:* give both methods the same search. Use the same grid, or the same number of trials, and the same rank or parameter budget. Make sure the grid brackets the optimum for each method. If the best value for either one sits at the edge of the grid, extend it.

**2. One seed each.** GSM8K's test set has 1,319 problems. At about 60% accuracy, the binomial standard error is roughly 1.3 points per model. That is test-set sampling noise alone. Training-seed variance (LoRA init, data order) comes on top of it, and fine-tuning runs on GSM8K often vary by a point or more between seeds. A 4-point gap is suggestive, but it isn't distinguishable from noise with n=1.

*Fix:* run at least 5 seeds per method at each method's best learning rate. Report mean and standard deviation. Use a paired bootstrap over test questions, or a paired test on per-question correctness, to show the gap holds.

**3. Where the learning rate was selected (please confirm).** You didn't say what you tuned the 6 values against. If it was the GSM8K test set, you have selection on test, and best-of-6 on test inflates your number on its own. If you used a held-out dev split, say so in the paper.

*Fix:* carve a dev set (for example 500 questions) out of the training split. Select the learning rate and any other hyperparameters there, and touch the test set once at the end.

## Serious

**4. No ablation isolating your contribution.** You need a table showing which part of your variant produces the gain. At minimum:

| Row | Purpose |
|---|---|
| Base model, no fine-tuning (same prompt and eval) | Lower bound |
| Standard LoRA, tuned | Main baseline |
| Standard LoRA at a matched trainable-parameter count (higher rank) | Rules out "more parameters" |
| Your method, full | The claim |
| Your method minus each component | Isolates the contribution |

Flag any components that interact. If you have two changes, test them alone and together. If compute is tight, the first three rows plus one removal per component is what a reviewer will insist on.

**5. Parameter and compute parity.** Check whether your variant has more trainable parameters, more memory, more FLOPs per step, or more steps than standard LoRA. If so, the comparison is not apples to apples. Report trainable parameters and wall-clock for every row.

**6. Missing stronger baselines.** Reviewers will expect comparison to other recent LoRA variants, not only the original. I can't search from here, so I won't name papers from memory. Search terms: "LoRA variants fine-tuning", "low-rank adaptation improvement", "parameter-efficient fine-tuning GSM8K", "rank-stabilized LoRA", "weight-decomposed LoRA", "LoRA learning rate sensitivity". Pick the 2 or 3 closest methods to yours, and run them with the same tuning protocol as everything else.

**7. One dataset, one model.** GSM8K alone is a narrow basis for a general claim about a LoRA variant. At minimum add a second model size or family. Ideally add a second task (MATH, a code or commonsense benchmark) so the claim is not specific to grade-school arithmetic.

## Minor

- **Eval protocol.** Fix and report the prompt format, decoding (greedy vs. sampling), answer extraction, and max tokens. Small differences here move GSM8K scores by several points, and they must be identical across arms.
- **Contamination.** Check whether the base model has seen GSM8K, since that affects how to interpret absolute numbers (not the comparison, if it is fair).
- **Report the learning-rate sensitivity curves** for both methods. If your method is simply less sensitive, that is a finding in itself.

## Budget

4 A100s for two weeks is generous for this. LoRA on a 7B model over GSM8K's roughly 7.5k training examples should take on the order of an hour or a few hours per run depending on epochs and sequence length (my estimate, so measure one run first). A plan:

1. Measure the time of one run.
2. Tune both methods on a dev split, same grid, 1 seed each: about 12 runs.
3. Final comparison: 5 seeds each at the best learning rate: 10 runs.
4. Ablations and the parameter-matched baseline: about 5 configs times 3 to 5 seeds.
5. Second model or task if time remains.

That is likely under 100 runs total, which should fit comfortably.

## Verdict

Don't write this up yet. Run the fair-tuning plus multi-seed comparison first. That is the cheap pilot that decides everything: if the gap survives equal tuning and 5 seeds with a paired test, you have a real result and a short list of ablations to finish. If it shrinks to about 1 point or less, you've learned that now rather than from a reviewer. Either way you will know in a few days.

What would change my mind: a gap of 3+ points that holds across seeds, with the tuned baseline and a parameter-matched baseline included, ideally on a second model.

One question that would sharpen this critique: what is the mechanism of your variant, and does it change the number of trainable parameters or compute? That determines which ablations and baselines are most important.
