An operation is **idempotent** if doing it several times has the same effect as doing it once. The result after the first call is the same as the result after the tenth.

Everyday examples:
- Pressing an elevator's "up" button repeatedly. The elevator still comes once.
- Setting a thermostat to 70°F. Setting it again changes nothing.
- Counterexample: pressing "add one" on a counter. Each press changes the state, so it is not idempotent.

In math terms, f(f(x)) = f(x).

## Why people care in APIs

Networks are unreliable. A client sends a request and then the connection drops, or the response times out. The client can't tell whether the server never got the request, processed it but the reply was lost, or is still working on it.

If the operation is idempotent, the client can simply retry. If it isn't, a retry might do the thing twice, for example charging a customer twice or creating duplicate orders.

That is the main reason idempotency matters. It makes retries safe, and that makes clients, queues, load balancers, and retry libraries much simpler and more robust. Many systems retry automatically, and a lot of delivery guarantees ("at-least-once") only work well if handlers are idempotent.

## HTTP methods

The HTTP spec defines which methods are meant to be idempotent:

- **GET, HEAD, OPTIONS**: idempotent (and also "safe", meaning they don't change anything).
- **PUT**: idempotent. It replaces a resource with the given representation, so sending the same PUT twice leaves the same end state.
- **DELETE**: idempotent. After the first call the resource is gone, and later calls leave it gone. The response code may differ (200, then 404), but the server state is the same.
- **POST**: *not* idempotent by default. "Create an order" twice usually creates two orders.
- **PATCH**: depends on the operation. "Set status to shipped" is idempotent. "Increment quantity by 1" is not.

Idempotent here refers to the effect on server state, not to getting an identical response each time.

## Making non-idempotent operations safe: idempotency keys

For things like payments, a common pattern is to have the client generate a unique **idempotency key** (usually a UUID) and send it in a header, such as `Idempotency-Key: 8f3c...`. The server records the key along with the result of the first request. If the same key arrives again, the server returns the stored result instead of doing the work again. Stripe and many other payment APIs work this way.

A few practical notes:
- Keys should be unique per logical operation, not per retry attempt.
- The server should store keys for a limited time, such as 24 hours.
- If the same key arrives with a different request body, the server should reject it rather than guess.

## Summary

Idempotency means repeating a request doesn't change the outcome beyond the first time. In APIs it is what lets clients retry after failures without risking duplicate side effects, which is important because in distributed systems you can never be fully sure whether a request went through.
