A race condition is a bug where a program's behavior depends on the timing or ordering of events that aren't properly controlled, usually when two or more threads, processes, or requests access shared data at the same time and at least one of them changes it.

**A simple example**

Say two threads each run `counter = counter + 1` on a shared counter that starts at 0. That one line is really three steps: read the value, add one, write it back. If the steps interleave like this:

1. Thread A reads 0
2. Thread B reads 0
3. Thread A writes 1
4. Thread B writes 1

the final value is 1, not 2. One update was lost. Run it again and the timing may differ, so you might get 2. That inconsistency is what makes race conditions hard to find.

**Why they're nasty**

- They're non-deterministic. The bug may show up once in a thousand runs, or only under heavy load.
- Adding logging or a debugger often changes the timing and hides the problem.
- They often pass in testing and fail in production.

**Common forms**

- **Read-modify-write races**, like the counter above.
- **Check-then-act races** (also called TOCTOU, time-of-check to time-of-use). You check a condition, such as "does this file exist?" or "is the seat available?", and act on it, but the condition changes in between.
- **Data races**, where unsynchronized threads access the same memory and at least one writes. In some languages, such as C and C++, this is undefined behavior.
- **Distributed races**, such as two web requests booking the same seat or two services updating the same database row.

**How to prevent them**

- **Avoid shared mutable state.** Use immutable data, or give each thread its own copy.
- **Use locks or mutexes** so only one thread at a time runs the critical section.
- **Use atomic operations**, such as atomic increments or compare-and-swap, for simple updates.
- **Use database transactions, constraints, or optimistic locking** (version checks) for data in a database.
- **Use message passing or queues** so one owner handles all changes to a piece of state.
- **Make operations idempotent**, so a repeat or reordering doesn't cause harm.

**How to find them**

Tools like ThreadSanitizer (C/C++/Go/Rust), Go's `-race` flag, and Java's concurrency analyzers can detect data races. Stress tests that run many threads repeatedly also help expose them.
