Idempotent means that doing something once has the same effect as doing it many times. The first run changes things. Repeat runs change nothing more.

A light switch marked "ON" is a good example. Press it once and the light is on. Press it five more times and the light is still on. A "toggle" button is not idempotent, because each press flips the state.

People care about it in APIs because networks fail. Say you send a request to charge a customer $50, and the connection drops before you get a reply. You don't know if the charge went through. If you retry and the request is not idempotent, you might charge them twice. If it is idempotent, you can retry as often as you like and the customer is charged once.

That's why it matters in practice:

- **Safe retries.** Clients, load balancers, and libraries can resend a request without fear of side effects.
- **Simpler client code.** You don't need to build logic to find out whether the first try worked.
- **Fewer bugs.** Duplicate messages and double clicks are common, and idempotent operations handle them well.

In HTTP, `GET`, `PUT`, and `DELETE` are meant to be idempotent. `POST` usually is not, since it often creates a new item each time. To make a `POST` safe to retry, many APIs let you send an idempotency key, which is a unique ID you pick for the request. If the server sees the same key twice, it returns the first result instead of doing the work again.
