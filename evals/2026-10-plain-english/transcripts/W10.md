A race condition is a bug where the result of your program depends on the timing of events that you don't control.

It usually happens when two parts of a program work at the same time and share the same data. Each part assumes it's the only one touching that data. If their steps interleave in an unlucky order, the data ends up wrong.

Here's a simple example. Two people use the same bank account. The balance is $100. Each of them tries to deposit $10 at the same moment.

1. Both read the balance: $100.
2. Both add $10 in their heads: $110.
3. Both write $110 back.

The balance should be $120, but it's $110. One deposit was lost. If the two deposits had happened one after the other, you'd get the right answer. That's why the bug is hard to catch. It only shows up on some runs, so it can be gone when you test it.

The usual fix is to make sure only one part can use the shared data at a time. You do this with a lock, or by making the read-and-update a single step that can't be split.
