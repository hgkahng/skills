Idempotent means that doing something many times has the same result as doing it once.

A light switch labeled "On" is a good example. Press it once and the light is on. Press it five more times and the light is still on. A switch that toggles is not idempotent, because each press changes the result.

In an API, this matters because requests sometimes fail in unclear ways. Say your app sends a request to charge a customer, and the connection drops before a reply comes back. You can't tell if the charge went through. If you send the request again and the charge isn't idempotent, the customer might be charged twice. If it is idempotent, you can safely retry, and the outcome is the same either way.

That's why people care. Idempotent requests make retries safe, which makes systems simpler and more reliable. Networks fail, so retries are normal.

Some common HTTP methods are idempotent by design. `GET` (read data), `PUT` (replace a record with this exact version), and `DELETE` (remove a record) all are. Deleting the same record twice leaves it gone. `POST` (usually "create something new") is not idempotent by default. Sending it twice can create two records.

To make a `POST` safe to retry, many APIs let you send an idempotency key. This is a unique ID you create for each action. If the server sees the same key twice, it doesn't repeat the work. It just returns the first result.
