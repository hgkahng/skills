A database index is a separate, sorted data structure that lets the database find rows without reading the whole table. It works like the index at the back of a book. You look up a term, get the page numbers, and jump straight there, instead of reading every page.

**The problem it solves**

Say you run `SELECT * FROM users WHERE email = 'a@example.com'` on a table with 10 million rows. With no index, the database does a full table scan. It reads every row and checks each one, so the work grows linearly with table size.

**How it works**

Most indexes are B-trees, or a variant called B+ trees. The index stores the values of the indexed column(s) in sorted order. Each value has a pointer to where the full row lives on disk.

- The tree has a root node, internal nodes, and leaf nodes.
- Each internal node holds ranges that tell you which child to follow, much like a binary search.
- Nodes are sized to fit a disk page, so the tree is wide and shallow. Even with hundreds of millions of rows it is usually only 3 or 4 levels deep.
- A lookup walks from the root to a leaf in a few steps (O(log n)), then follows the pointer to the row.

So finding one row among 10 million takes about 3 or 4 page reads instead of scanning the whole table.

In B+ trees the leaf nodes are also linked together in order. That makes range queries (`WHERE created_at BETWEEN ...`), `ORDER BY`, and prefix searches (`LIKE 'abc%'`) efficient. The database finds the start of the range and then walks along the leaves.

**Other index types**

- **Hash indexes** are very fast for exact-match lookups (`=`) but can't do ranges or ordering.
- **Bitmap indexes** suit low-cardinality columns, such as a status flag, mostly in analytics systems.
- **Full-text, GIN, and GiST indexes** support text search, arrays, JSON, and geospatial data.

**Clustered vs. non-clustered**

- A **clustered index** determines the physical order of the rows themselves. The table is stored in the index's order, so there can be only one per table. In MySQL's InnoDB, the primary key plays this role.
- A **non-clustered (secondary) index** is a separate structure that points back to the rows. A table can have many of these.

**Trade-offs**

Indexes speed up reads but are not free:

- **Slower writes.** Every `INSERT`, `UPDATE`, and `DELETE` must also update each affected index, and sometimes split or rebalance nodes.
- **Extra storage.** Each index takes up disk space and memory.
- **The planner may ignore them.** If a query will return a large fraction of the table, a full scan can be cheaper than bouncing through the index.

**Practical tips**

- Index columns you frequently use in `WHERE`, `JOIN`, and `ORDER BY` clauses.
- For composite indexes, column order matters. An index on `(last_name, first_name)` helps queries on `last_name` alone, but not on `first_name` alone.
- Wrapping an indexed column in a function (for example `WHERE LOWER(email) = ...`) usually prevents the index from being used, unless you create an expression index.
- Use `EXPLAIN` (or `EXPLAIN ANALYZE`) to check whether a query actually uses your index.
