**Intent.** A review comment should be worth the author's attention: each one should change what the author does, and the reviewer's attention goes to the few things that matter in the PR.

**Ladder.** Why would those five rules all be wanted? Each targets a comment that costs the author a read and gives back no decision: nits, formatting (a linter's job), renames (taste), praise (no action). The cap of 5 is a proxy for the same thing, since low-value comments crowd out high-value ones. One step up: the author's attention is scarce, so a comment is justified by the change it causes. Higher than that ("be helpful") excludes nothing.

---

**Principle**
Write a comment only if the author would act on it: it points to something that is wrong, risky, or unclear in a way that affects correctness, security, maintainability, or the behavior the PR intends. Rank by consequence and lead with the most serious.

**Why**
The author has limited attention, and every comment spends some of it. Comments that don't change the code still cost a read and a decision, and they bury the one comment that matters. Style is better enforced by tools, which are consistent and don't spend reviewer judgment. A short review of consequential findings gets read and acted on. A long one gets skimmed.

**Derived anchors**
- Hence: no "nit:" comments. If it's worth raising, state why it matters; if you can't, leave it out.
- Hence: no formatting comments. A formatter or linter owns that.
- Hence: there is usually no need for more than about 5 comments. If you have more, keep the highest-consequence ones and fold related findings into one.
- Hence: don't propose renames or give praise as such. A name only merits a comment when it actively misleads, and then the comment is about the misleading behavior, not the name.

**Boundary**
- Cut low-value comments, not substance. If there are 7 real defects, don't hide 2 to hit a number. Say plainly that the PR has more problems than you listed, and group them or flag the PR as needing rework.
- Silence is not approval. If you found nothing worth a comment, say what you checked, so the author knows the review happened.
- Don't suppress a formatting or naming issue that causes a bug (e.g. misleading indentation that changes how the code reads, a name that implies the wrong units).
- Noting something that works and is non-obvious (a subtle invariant the author handled) is acceptable when it tells later readers not to change it. That is information, not praise.
- Hard constraints, which have no deeper principle behind them: none identified. The 5-comment cap is derived above as a default, not a hard limit. If you need it as a strict cap, say so and it should be kept as a plain rule.
