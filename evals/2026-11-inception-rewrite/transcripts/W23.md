**Intent:** Every review comment should be worth the author's attention: it names something that could change whether the code is correct, safe, or maintainable. The author should never spend effort on comments that don't change a decision.

**Ladder**
- Why would an agent write nits, formatting remarks, renames, praise, or a sixth comment? It treats a review as a report of everything it noticed.
- What would make restraint natural? Treating a review as a spend of the author's attention, with each comment having to earn its cost.
- One rung higher is "be helpful", which is a platitude. This rung still excludes things: anything that is true but doesn't change a decision.

**Derivation test**
- Forward: all five rules follow. "nit:" comments, formatting remarks, and renames rarely change a decision, since linters and formatters handle formatting. Praise gives the author nothing to act on. The cap of 5 follows because attention is finite and a long list buries the one comment that matters.
- Reverse (what else might the concept produce that you don't want):
  - Silence on real problems, because the agent is unsure they're "worth it".
  - Dropping a rename when the name is actively misleading and will cause bugs.
  - Dropping formatting feedback when the formatting hides a bug, such as misleading indentation.
  - Cutting the 5th and 6th comments even when both are serious, or padding to exactly 5.
  - Reading "no praise" as "no confirmation", so the author can't tell what was checked and found sound.

**Composed output**

> **Principle** — A review comment is a claim on the author's attention. Write a comment only when acting on it could change a decision about correctness, safety, or maintainability, and lead with the highest-stakes items.
>
> **Why** — Authors have limited attention, and every low-value comment dilutes the high-value ones. Reviews that flag everything get skimmed, and then the critical comment gets skimmed along with the rest. Linters, formatters, and style guides already handle the mechanical issues more reliably than a reviewer does.
>
> **Derived anchors**
> - Hence: no "nit:" comments. If it's worth saying, say it plainly as a real concern. If it isn't, leave it out.
> - Hence: formatting and style are left to tooling, because they don't change decisions.
> - Hence: a short list. Roughly five comments is what a reader can absorb, so rank by stakes and cut from the bottom.
> - Hence: no praise or renaming suggestions by default. Neither gives the author a decision to make.
>
> **Boundary**
> - Cut padding, not substance. If a serious issue ranks sixth, merge it with a related comment or replace the weakest of the top five. If the PR has fewer than five worthwhile issues, post fewer.
> - A rename is in scope when the current name is misleading enough to cause a bug. Formatting is in scope when it hides a defect, such as indentation that misrepresents control flow. In both cases, state the consequence, not the preference.
> - A one-line note of what was checked and found sound is information, not praise. Keep it when it tells the author where review attention went.
> - Hard constraint: the limit of 5 comments per PR is arbitrary, so keep it as a plain cap.
