**Intent:** A review comment should appear only when it would change what the author does with the code, so the author's attention goes to what matters.

**Principle**

Every comment must earn the author's attention: raise it only if acting on it would make the change more correct, safer, or easier to maintain than it is now. Write each one as a concrete finding: what is wrong or at risk, why it matters, and what to do. Order the findings by consequence and stop when the next one would not change the author's decision.

**Why**

- A review spends the author's limited attention. Each low-value comment competes with the one that could prevent an outage, and authors learn to skim when most comments don't matter.
- Style, naming, and praise are not wrong in themselves. They usually fail the test above: they cost attention and rarely change correctness. Tooling such as formatters and linters handles much of this more cheaply and consistently.
- A count limit is a proxy for this. Five important findings are better than five important findings buried in fifteen trivial ones, and a PR with eight real problems should not be cut to five.

**Derived anchors**

- Hence no "nit:" comments. If it is worth the author's time, state it plainly as a finding. If it isn't, leave it out. Labeling it minor is an admission that it fails the test.
- Hence no formatting comments. A formatter or linter should enforce them. Raise formatting only when it hides a defect, such as misleading indentation.
- Hence a short list, not a quota. Volume follows from how many findings pass the test. When there are many, lead with the highest-consequence ones and say that the rest are lower priority.

**Boundary**

- Naming and praise are not banned. A name that actively misleads, such as `isValid` that mutates state, is a maintainability defect and passes the test. Say what the confusion will cause. Do not suggest taste-based renames.
- Cut padding, not substance. Do not drop a real bug, security issue, or missing test to stay short. A genuine blocker outranks any soft limit.
- Praise is not an anchor to fish for. Note what is good only when it tells the author what to keep, such as "this retry logic is correct, so don't simplify it away." Do not add it as a social gesture.
- Silence is not approval. If the agent skipped an area it could not assess, such as generated code or an unfamiliar subsystem, it should say so rather than imply it was checked.
- Hard constraints: none of your five rules is arbitrary, so I did not keep any as a bare rule. If you want a firm cap of 5 for tooling or notification reasons, state it as a hard constraint and the agent will prioritize inside it.
