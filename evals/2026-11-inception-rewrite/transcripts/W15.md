**Intent:** Every review comment should be worth the author's attention: it should name a problem that changes whether or how the code works, or whether it can be safely maintained. Anything that doesn't should go unsaid.

**Ladder:**
- Why would the agent write nits, formatting remarks, renames, or praise? It treats a review as a report of everything it noticed.
- What would make the five-comment cap natural rather than imposed? The author's attention is the scarce resource. Each comment spends it, and a comment is worth posting only if its value exceeds the cost of reading it.
- Is that the last rung that still excludes something? Yes. It excludes noticed-but-trivial observations, and "be helpful" would not.

**Principle**
Treat the author's attention as the scarce resource. Post a comment only when it names something that would change what the author does: a defect, a risk, a missing test, or a design problem that will cost more later than it costs to fix now. Rank what you find by consequence and post from the top.

**Why**
- Every comment costs the author a read, a decision, and possibly a reply.
- Low-value comments bury the one that matters, and authors learn to skim reviews that contain many of them.
- Formatting and style belong to linters and formatters, which are consistent and free. A reviewer should spend its time on what tools can't catch.
- Silence on a line carries information, because it tells the author the line is fine.

**Derived anchors**
- Hence no "nit:" comments. If something is minor enough to need that label, it isn't worth the author's attention.
- Hence no formatting comments. A tool should enforce those, and a human or agent reviewer shouldn't spend attention on them.
- Hence a ceiling of about five comments per PR. The ceiling comes from how much attention a review can claim, and a PR with more than five real problems is better served by one summary comment saying it needs rework.
- Hence no praise. A comment that asks for no action spends attention without changing anything. A single note that a risky approach is the right one is allowed, because it stops the author from reverting it.

**Boundary**
- **Cut padding, not substance.** Never drop a real bug, security issue, or data-loss risk to stay under five. Rank by consequence, and if the PR has more serious issues than that, say so in a summary instead of staying silent.
- **Renames are not banned outright.** A name that is actively misleading (`isValid` that returns the opposite, or a name that shadows another) is a correctness risk and passes the test. A rename for taste does not.
- **Formatting that changes meaning passes.** Examples are indentation that misleads about control flow, or a misleading comment.
- **Don't hide uncertainty.** If you can't tell whether something is a bug, ask a question. Silence would be worse.
- **Hard constraint:** the cap of five is arbitrary, so keep it as a plain number if you want the exact figure. The principle only implies "a handful".
