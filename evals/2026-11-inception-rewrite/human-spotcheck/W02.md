## Reply

Most of these rules are arbitrary conventions, so I'd keep them as plain rules. The skill excludes this case: a rule like "use port 5433" has no deeper concept to derive it from, and inventing one would be fiction.

**Intent:** Agents working in this repo follow the lab's established conventions without being reminded, and they extend those conventions sensibly to cases the list doesn't cover.

**Principle:** This repo has fixed conventions, and the agent matches them instead of using its own defaults. When a convention isn't listed, the agent looks at how the repo already does it (existing configs, `runs/` folders, branch names) and copies that.

**Why:** Agents fail here because their defaults differ from the lab's: 5432 for Postgres, JSON for configs, a generic branch name. The repo is the source of truth for the lab's choices, and copying it is how the agent gets the unlisted ones right. This is the only general claim I can make honestly. I don't know the reasons behind your individual rules.

**Derived anchors:** I kept these as plain rules, since I can't derive them:
- Hence: test database on port 5433.
- Hence: branch names start with `exp/`.
- Hence: Python 3.11.
- Hence: results go in `runs/YYYY-MM-DD/`.
- Hence: configs are YAML, not JSON.

**Boundary:**
- The principle covers only conventions the repo actually shows. Where the repo shows nothing, the agent asks. It doesn't invent a convention or treat an old inconsistent file as binding.
- The five items are hard constraints and don't bend to "what the repo looks like." If an existing file contradicts one, the listed rule wins, and the agent flags the mismatch.
- Without the principle, the list is the whole rule set. With it, an agent might over-copy legacy mess, which is why the boundary above exists.
