These five rules don't have a principle behind them, so I wouldn't write one. Each is an arbitrary convention, like the skill's own examples "use port 8080" and "branch names start with `feat/`". A unifying idea such as "keep the lab repo consistent" would be a platitude that guides nothing. Anything more specific would be fiction, because the port, branch prefix and YAML choice don't follow from a shared reason. A made-up "why" would also fail as soon as the context contradicted it.

**Principle**: None. This is a set of independent conventions.

**Why**: None to state honestly. If you know the real reason for any of them, add it, because a true reason helps an agent handle cases the rule doesn't cover. For example:
- If 5433 avoids a clash with a local Postgres on 5432, an agent will know to check for a port conflict instead of changing the port.
- If YAML is there for comments and readability, an agent will know to write new config files, including ones nobody anticipated, in YAML.
- If `runs/YYYY-MM-DD/` is for reproducibility, an agent will know to record the config and commit alongside the results.

**Derived anchors**: None.

**Boundary / hard constraints** (keep these as plain rules):
- Test database port: `5433`.
- Branch names start with `exp/`.
- Python version: `3.11`.
- Results go in `runs/YYYY-MM-DD/`.
- Config files are YAML, not JSON.

**Where to put it**: `AGENTS.md`, since these apply to every task in the repo. I haven't written anything to a file. If you tell me the file and give me any of the real reasons above, I'll add them as one-line "because…" notes next to the rules.
