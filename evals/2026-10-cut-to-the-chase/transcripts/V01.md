# Hunting a memory leak in a Node.js service

A memory leak is memory your program keeps holding after it no longer needs it, so the garbage collector (GC) cannot free it. The process's memory grows until it is slow or crashes with "JavaScript heap out of memory" or is killed by the OS or container (OOM kill).

The method: confirm it is a leak, reproduce it, take heap snapshots, compare them, find what holds the objects, fix, and verify.

## Step 1: Confirm it is a leak, and which kind

Not all growth is a leak. Memory normally rises after startup and after load, then levels off. A leak is growth that continues under steady load and never comes back down after GC.

Watch these numbers from `process.memoryUsage()`:

- `heapUsed`: live JavaScript objects. This is the main one.
- `heapTotal`: heap the V8 engine has reserved.
- `rss`: total memory the process uses from the OS.
- `external` and `arrayBuffers`: memory outside the JS heap, such as Buffers.

Log them periodically:

```js
setInterval(() => {
  const m = process.memoryUsage();
  console.log(JSON.stringify({
    rssMB: (m.rss / 1048576).toFixed(1),
    heapUsedMB: (m.heapUsed / 1048576).toFixed(1),
    externalMB: (m.external / 1048576).toFixed(1),
    arrayBuffersMB: (m.arrayBuffers / 1048576).toFixed(1),
  }));
}, 10_000).unref();
```

Read the pattern:

- `heapUsed` climbs steadily in a sawtooth whose lows keep rising: a JS-heap leak. Continue with this guide.
- `heapUsed` is flat but `rss`, `external` or `arrayBuffers` climbs: the leak is outside the JS heap (Buffers, native addons, unclosed streams or sockets). Heap snapshots will not show the cause directly. See "Leaks outside the heap" at the end.
- Memory rises then plateaus: probably not a leak, just a cache or warm-up. If the plateau is too high for your container, tune it (see the `--max-old-space-size` note in the last section).

To force the question, run with `node --expose-gc` and call `global.gc()` before logging. If `heapUsed` still rises after a forced GC, it is a real leak.

## Step 2: Reproduce it in a controlled setting

You want to trigger the leak on demand, fast, with a process you can inspect. Debugging in production is a last resort.

1. Run the service locally or in staging with the same code and configuration.
2. Generate load with a tool such as `autocannon`, `k6`, or `wrk`, hitting the endpoints you suspect:
   ```
   npx autocannon -c 50 -d 120 http://localhost:3000/some/endpoint
   ```
3. Watch the memory log from Step 1. Narrow it down: hit one endpoint at a time until you find the one whose repeated use makes `heapUsed` rise.

Knowing which request or job triggers the growth saves hours later.

## Step 3: Start the process so you can take snapshots

A heap snapshot is a dump of every live object in the JS heap and what references it. There are three ways to get one.

**A. Inspector with Chrome DevTools (best for local work)**

```
node --inspect server.js
```

Open `chrome://inspect` in Chrome, click "inspect" under your Node process, and go to the Memory tab. Choose "Heap snapshot" and click "Take snapshot".

If the process is in a container or remote machine, forward the port (`--inspect=0.0.0.0:9229` plus a port forward or SSH tunnel). Never expose the inspector port publicly; it gives full control of the process.

**B. Signal-triggered snapshots (good for staging and production)**

```
node --heapsnapshot-signal=SIGUSR2 server.js
kill -USR2 <pid>
```

Each signal writes a `.heapsnapshot` file into the working directory. Open it in DevTools: Memory tab, "Load".

**C. In code**

```js
const v8 = require('node:v8');
v8.writeHeapSnapshot();           // returns the filename it wrote
```

Wire it to an authenticated admin route or a signal if you need it on demand.

Warning: taking a snapshot pauses the process and can need roughly double its heap in extra memory. On a large heap in a memory-constrained container, it can trigger the OOM kill you are investigating. Give it headroom or do it on a staging copy.

## Step 4: Take three snapshots (the 3-snapshot technique)

This is the standard way to separate leaked objects from normal churn.

1. Start the service and send a little warm-up traffic so lazy initialization and caches are filled. Wait a moment.
2. **Snapshot 1** (baseline).
3. Run a batch of the suspect operation, for example 1,000 requests to the suspect endpoint. Wait a few seconds for GC.
4. **Snapshot 2**.
5. Run the same batch again.
6. **Snapshot 3**.

Use the same number of operations each time so growth is attributable to them.

## Step 5: Compare snapshots

In DevTools, select Snapshot 3 and change the view dropdown from "Summary" to "Comparison". Choose Snapshot 2 as the one to compare against. (Snapshot 1 vs 2 is also useful.)

Columns to read:

- **# New**: objects allocated since the earlier snapshot and still alive.
- **# Deleted**: objects freed.
- **# Delta**: new minus deleted. Sort by this, descending.
- **Alloc. Size / Freed Size / Size Delta**: the same in bytes.

What you are looking for: a constructor whose Delta is positive and proportional to your workload. If you sent 1,000 requests per batch and see about +1,000 `RequestContext` objects (or +1,000 of some closure, string, or array) in each comparison, that is your leak.

Common constructor names and what they usually mean:

- `(closure)`: functions holding references through their scope. Often a leaked listener or callback.
- `(string)` / `(concatenated string)`: large numbers of strings, often cache keys or accumulated log or response data.
- `Array`, `Object`, `Map`, `Set`: a collection that grows. Look at who owns it.
- `Promise`: promises never settled, or chains that never end.
- `Buffer` / `ArrayBuffer`: raw binary data being retained.
- Your own class names: usually the clearest signal.

Ignore anything whose delta is small or does not repeat between snapshots. Early growth that does not continue is warm-up.

## Step 6: Find what is holding the objects (retainers)

An object is only leaked if something still references it. Click one of the suspect instances. The **Retainers** panel at the bottom shows the chain of references from a GC root down to that object.

How to read it:

- Follow the chain upward until you reach something recognizable from your code: a module-level variable, a long-lived object, an event emitter, a timer, a cache.
- **Shallow size** is the object's own memory. **Retained size** is the memory that would be freed if the object were deleted, including everything only it keeps alive. Sort by retained size to find the expensive holders.
- Paths through `system / Context` or `(closure)` mean a function's scope is keeping variables alive. Expand `context` to see which variables. A closure often captures far more than the developer intended, because all closures in the same scope share one context.
- In the Summary view, the "Distance" column is how far an object is from a GC root. A short distance with a huge retained size is a strong lead.

If the retainer path ends at one of your module-level variables or a long-lived object, you have found where to look in the code.

## Step 7: Map the finding to the usual causes

Check the retainer against this list of what actually leaks in Node services.

1. **Unbounded caches and maps.** A module-level `Map`, object, or array that is added to on each request and never evicted. Fix: set a size or time limit (for example the `lru-cache` package), or store with a TTL.
2. **Event listeners never removed.** `emitter.on(...)` called per request or per connection, without a matching `off`. Node warns "MaxListenersExceededWarning: Possible EventEmitter memory leak detected"; treat that warning as a real lead. Fix: remove listeners on cleanup, use `once` where appropriate, and attach listeners to per-request objects rather than shared ones.
3. **Timers never cleared.** `setInterval` that is never cleared, or timers that capture large objects in their callback. Fix: `clearInterval` on teardown, and call `.unref()` on timers that should not keep the process alive.
4. **Closures capturing large objects.** A callback stored somewhere long-lived that closes over a request, response, or big payload. Fix: capture only the fields you need, or null out references when done.
5. **Global state and module-level accumulators.** Arrays that collect results, metrics, or logs forever. Fix: bound them or flush them.
6. **Per-request resources not released.** Database connections, streams, file handles, HTTP agents, or sockets not closed on error paths. Fix: always release in `finally`, handle `error` and `close` events, and use `stream.pipeline` instead of manual `.pipe` so streams are destroyed on failure.
7. **Promises that never settle.** Awaiting something that never resolves (no timeout), keeping its whole closure alive. Fix: add timeouts and abort signals.
8. **Memoization with unbounded keys.** Memoizing a function by an argument with unlimited variety (user IDs, URLs, timestamps). Fix: bound the memo, or use a `WeakMap` when the key is an object.
9. **Third-party libraries.** Check the library's issue tracker and version for known leaks, especially for logging, tracing/APM agents, and HTTP clients.

## Step 8: Use allocation tracking when snapshots are not enough

If snapshot comparison shows the type but not the code that creates it, use allocation profiling in the DevTools Memory tab:

- **Allocation instrumentation on timeline**: records every allocation with its stack trace while you run load. Blue bars on the timeline are allocations still alive; they turn grey when freed. Select a time range with persistent blue bars and the list shows the constructors and the call stacks that allocated them. This points straight at the line of code.
- **Allocation sampling**: lower overhead, suitable for longer runs or heavier load, giving approximate allocation sites by function.

Run it against the same reproduction from Step 2. It slows the process noticeably, so lower the load.

## Step 9: Fix it, then verify

1. Make the smallest change that removes the retainer you identified (bound the cache, remove the listener, clear the timer, close the resource).
2. Rerun the exact reproduction from Step 2 with the memory log from Step 1.
3. Confirm: `heapUsed` after forced GC now returns to a stable level between batches, and the Step 5 comparison no longer shows a growing delta for that constructor.
4. Repeat the three-snapshot process once more. Services often have more than one leak; fixing the biggest one reveals the next.
5. Keep the check: add a soak test or a memory alert so a regression is caught. Alert on `heapUsed` after GC trending up over hours, not on raw RSS spikes.

## Leaks outside the heap

If `heapUsed` is flat but `rss` keeps rising:

- Look at `external` and `arrayBuffers` in `process.memoryUsage()`. Growth there means Buffers or typed arrays are retained. The heap snapshot shows the small JS wrapper objects, so search it for `Buffer` and `ArrayBuffer` retainers.
- Suspect native addons (image processing, crypto, database drivers) that allocate native memory and rely on you calling a close or free method.
- Suspect unclosed sockets, file descriptors, or streams. Check with `lsof -p <pid> | wc -l` repeated over time; a rising count means handles are leaking.
- Glibc memory fragmentation can inflate RSS without a leak. Setting `MALLOC_ARENA_MAX=2` or using `jemalloc` sometimes flattens it. Rule out a real leak first.
- Use OS tools for native memory: `pmap`, or `heaptrack`/`valgrind` on a staging process.

## Practical notes

- `--max-old-space-size=<MB>` raises the heap limit. It delays the crash; it does not fix a leak. In containers, set it comfortably below the container memory limit (for example about 75 percent) so Node fails with a clear error instead of an OOM kill.
- `node --heap-prof` writes a sampling allocation profile on exit, useful when you cannot attach DevTools.
- `node --report-on-fatalerror` (or `--report-on-signal`) writes a diagnostic report with memory stats when the process dies.
- Take snapshots from a process that has handled real traffic for a while, not a freshly started one. Comparing against a cold baseline makes warm-up look like a leak.
- Snapshot files can contain sensitive data (tokens, user data, secrets in memory). Treat them as confidential and do not share them freely.
- Load a snapshot in DevTools on a machine with enough RAM; a 1 GB snapshot needs several GB to open.
