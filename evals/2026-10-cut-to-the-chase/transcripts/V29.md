Hunt a Node.js leak by confirming it, capturing heap snapshots at different times, diffing them, and tracing the growing objects back to the code that retains them. Steps:

## 1. Confirm it is a leak

A leak is memory that keeps growing under steady load and never comes back down after garbage collection (GC). A high but flat number is not a leak.

- Watch `process.memoryUsage()` over time (log it every 30 seconds) or use your metrics tool:
  - `rss`: total memory the process holds from the OS.
  - `heapUsed`: live JavaScript objects. This is the number to trust.
  - `external` and `arrayBuffers`: Buffers and native memory outside the V8 heap.
- Leak signature: after each GC, the low points of `heapUsed` keep rising (a sawtooth with a rising floor).
- If `rss` grows but `heapUsed` stays flat, the leak is outside the JS heap (Buffers, native addons, fragmentation). Go to step 8.
- Check that the growth correlates with traffic. If it grows with no requests, look at timers, caches, and background jobs.

## 2. Make it reproducible

- Reproduce in a staging or local environment with the same Node version and flags.
- Drive steady load against the suspect endpoints (`autocannon`, `k6`, `wrk`, or a simple loop).
- Reduce the search area: hit one endpoint at a time and see which one makes the floor rise.
- Start the process with an inspector and a heap limit that makes the problem show up faster:

```bash
node --inspect --max-old-space-size=256 server.js
```

## 3. Take heap snapshots

A heap snapshot is a dump of every live object and what references it.

Three ways to take one:

- **Chrome DevTools:** open `chrome://inspect`, click "inspect" on your process, go to the Memory tab, choose "Heap snapshot", and click Take snapshot.
- **On a signal, no debugger needed:**

```bash
node --heapsnapshot-signal=SIGUSR2 server.js
kill -USR2 <pid>
```

  This writes a `.heapsnapshot` file into the working directory.
- **From code:**

```js
require('v8').writeHeapSnapshot();
```

Warnings:

- Taking a snapshot pauses the process and can need up to about twice the heap size in extra memory. Do not do this casually on a production pod near its memory limit. Prefer one instance that is pulled from the load balancer first.
- Snapshot files can contain secrets, tokens and user data. Treat them as sensitive.

## 4. Use the three-snapshot technique

1. Warm up the service: send some traffic so lazy initialization, caches and connection pools are filled. Otherwise normal start-up growth looks like a leak.
2. Take **snapshot A**.
3. Run a fixed amount of load (for example 10,000 requests to the suspect endpoint).
4. Force a GC (the trash can icon in DevTools, or run with `--expose-gc` and call `global.gc()`), then take **snapshot B**.
5. Run the same load again, force GC, and take **snapshot C**.

Anything that grew from A to B and again from B to C is a leak candidate. Things that grew only once are usually caches or lazy initialization.

## 5. Compare the snapshots

In DevTools, load all three files in the Memory tab.

1. Select snapshot C, change the view from "Summary" to **Comparison**, and pick snapshot B as the baseline.
2. Sort by **# Delta** (count of new objects) or **Size Delta**.
3. Look for constructors whose count rises by roughly the number of requests you sent (about 10,000 extra objects of one type is a strong hint).
4. Ignore noise: `(compiled code)`, `(system)`, and similar entries are internal.
5. Common suspects at the top:
   - `(string)`, `Object`, `Array`: need a closer look at what holds them.
   - Your own classes (`Session`, `RequestContext`, `Connection`).
   - `Closure`, `Promise`, `Timeout`, `EventEmitter`.
   - `Buffer`/`ArrayBuffer`.

## 6. Find what is keeping the objects alive

Expand a leaking constructor and click a single instance. The **Retainers** panel at the bottom shows the chain of references from a GC root down to that object. The leak is the chain, not the object.

How to read it:

- Follow the retainer chain upward until you reach something that you wrote or imported and that lives for the whole life of the process: a module-level variable, a global `Map`, a singleton, an emitter, a timer.
- Distance matters: the shortest path to a root is what blocks collection.
- Weak edges (shown in grey) do not keep objects alive. Ignore them.
- Use the **Containment** view to browse from the root downward and see which large structures hold the most memory (check "Retained Size", the memory freed if that object disappeared, rather than "Shallow Size").

## 7. Match the pattern to a known cause

| Pattern in the snapshot | Typical cause | Fix |
|---|---|---|
| A module-level `Map`/`Object`/`Array` that keeps growing | Unbounded cache or registry | Add a size limit and eviction (`lru-cache`), or a TTL; delete entries when done |
| Many `Closure` or `Context` entries retaining big objects | Closures capturing large variables that outlive the request | Narrow what the closure references; null out large references; avoid long-lived callbacks |
| Growing `EventEmitter` listener arrays, or `MaxListenersExceededWarning` | `.on()` called per request or per connection without `.off()` | Remove listeners on close, use `.once()`, register once at start-up |
| Many `Timeout` / `Timer` objects | `setInterval` never cleared, or timers created per request | `clearInterval`/`clearTimeout` on teardown; call `.unref()` for background timers |
| Many pending `Promise` objects | Promises that never resolve, or unbounded queues of work | Add timeouts, backpressure, and queue limits |
| Request, response, or socket objects accumulating | Streams not ended or destroyed, keep-alive connections not closed, error paths that skip cleanup | Use `stream.pipeline`, handle `error` and `close`, destroy sockets on abort |
| Growing `Array` of log or metric entries | In-memory buffers that are never flushed | Flush on size or time; cap length |
| Large sliced strings | A tiny substring keeps a huge parent string alive | Copy the substring (for example `Buffer.from(s).toString()`) or avoid holding it |
| Growth in labels/keys of a metrics client | High-cardinality labels (user IDs, URLs as label values) | Reduce label cardinality |
| Global state attached to `global`, `process`, or `require.cache` | Accidental globals, repeated dynamic `require`/`import` | Use `const`/`let`, avoid dynamic module loading in hot paths |

## 8. If the heap is flat but RSS grows

The leak is native or fragmented memory.

- Compare `external` and `arrayBuffers` in `process.memoryUsage()`. Growth there points to Buffers: unreleased streams, large buffers cached somewhere, or native addons (image processing, compression, database drivers).
- Use the **Allocation sampling** profile in the DevTools Memory tab to see JS call stacks that allocate the most, including Buffers.
- If neither shows it, suspect a native addon or the allocator. On Linux with glibc, fragmentation can inflate RSS; try `MALLOC_ARENA_MAX=2` or the `jemalloc` allocator and see if RSS stabilizes.
- Test by disabling modules one at a time (for example swap the compression or image library) and see if the growth stops.

## 9. Use allocation tracking to find the exact line

If the snapshot diff tells you what leaks but not where it is created:

- In DevTools Memory, choose **"Allocation instrumentation on timeline"**, start recording, run the load, and stop. Blue bars are allocations still alive; grey bars were freed. Select a blue bar to see the stack that allocated those objects.
- This is heavier than snapshots, so use it in a local or staging reproduction only.

## 10. Fix it and prove the fix

1. Make one change at a time.
2. Re-run the same load test and the same three-snapshot comparison.
3. Success means the post-GC floor of `heapUsed` is flat over a long run (at least several times the period it took to show the leak before), and the constructor delta that was growing is now near zero.
4. Add a regression guard:
   - A test that runs the operation in a loop, forces GC (`--expose-gc`), and asserts that `heapUsed` growth stays under a threshold.
   - A production alert on the heap floor trend, not on the raw value.
5. Deploy gradually and watch the metric for a full traffic cycle (a day if usage is daily-cyclic).

## 11. Production tips

- Always set a memory limit consistent with the heap: `--max-old-space-size` should be below the container limit (leave room for Buffers and native memory), or the container will be OOM-killed before Node reports anything.
- Enable `--heapsnapshot-near-heap-limit=1` (Node 16 and later) so Node writes a snapshot just before it runs out of memory. This captures the leak at its worst, with no manual timing.
- Keep the process running with `--report-on-fatalerror` for diagnostic reports.
- Take snapshots from an instance with realistic traffic, not an idle one.
- Tools that help beyond DevTools: `clinic.js` (`clinic heapprofiler`), `memlab` (automated leak detection from a scripted scenario, and good for CI), and `heapdump`/`v8.getHeapStatistics()` for custom reporting.

## Quick checklist

1. Plot `heapUsed` after GC: is the floor rising?
2. Reproduce with steady load on one endpoint.
3. Snapshot A, load, GC, snapshot B, load, GC, snapshot C.
4. Compare C against B by delta; find the constructor growing with request count.
5. Read the Retainers chain to the long-lived root.
6. Fix the retention (cap, remove listener, clear timer, end stream).
7. Re-run and confirm the floor is flat; add a regression test and an alert.
