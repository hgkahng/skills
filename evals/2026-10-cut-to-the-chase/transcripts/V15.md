Method: confirm the leak, capture heap snapshots at intervals, diff them, follow retainers to the root, fix, and verify under load.

## Step 1: Confirm it is a leak

Not every memory growth is a leak. Node's heap grows until GC runs, and RSS can stay high after GC because of allocator behavior.

1. Watch `process.memoryUsage()` (log it every 10-30s, or export it to Prometheus/Datadog):
   - `heapUsed`: live JS objects. A leak shows here.
   - `heapTotal`: V8's reserved heap.
   - `rss`: total process memory.
   - `external` and `arrayBuffers`: Buffers and native memory outside the V8 heap.
2. Look at the trend over hours, not minutes. A leak is a sawtooth whose floor (the post-GC minimum) keeps rising. A flat floor means normal GC behavior.
3. Classify by which number grows:
   - `heapUsed` rises: JS objects are retained. Use heap snapshots (Steps 3-5).
   - `rss` and `external`/`arrayBuffers` rise but `heapUsed` is flat: Buffers, native addons, streams, or sockets. Go to Step 7.
   - `rss` rises but nothing else does: possible allocator fragmentation. Try `MALLOC_ARENA_MAX=2` or jemalloc.
4. Check that you are not just hitting a container limit. Node's default old-space cap depends on available memory and version. Set it explicitly with `--max-old-space-size=<MB>` to make behavior predictable.

## Step 2: Reproduce it in a controlled setting

You need a repeatable way to make memory grow.

1. Run the service locally or in staging with the same Node version and the same build.
2. Start with `--inspect` (or `--inspect=0.0.0.0:9229` in a container, only on a private network):
   ```
   node --inspect server.js
   ```
   Or send `SIGUSR1` to a running process to enable the inspector.
3. Generate load against the suspect endpoints with autocannon, k6, or wrk:
   ```
   npx autocannon -c 50 -d 120 http://localhost:3000/suspect-route
   ```
4. Bisect by route or feature: hit one endpoint at a time and watch which one makes the post-GC floor climb. This narrows the search before you open a single snapshot.
5. If it only leaks in production, use the production-safe options in Step 8.

## Step 3: Take heap snapshots (the three-snapshot technique)

1. Open `chrome://inspect` in Chrome, click "inspect" on your Node target, and go to the Memory tab. (VS Code's debugger and WebStorm can also do this.)
2. Warm up first: send a burst of traffic so lazy initialization, caches, and JIT are settled. Otherwise your diff is full of one-time allocations.
3. Click "Collect garbage" (the trash-can icon) to force a GC.
4. Take Snapshot 1 (baseline).
5. Run a fixed amount of load, for example 1,000 requests to the suspect route.
6. Force GC again and take Snapshot 2.
7. Run the same amount of load again, force GC, and take Snapshot 3.

Why three: objects that exist in 2 but not 1 may be warm-up. Objects that keep growing from 1 to 2 to 3 are your leak.

Programmatic alternative (no DevTools, good for servers you cannot attach to):
```js
const v8 = require('v8');
// writes a .heapsnapshot file you can load into DevTools
v8.writeHeapSnapshot(`/tmp/heap-${Date.now()}.heapsnapshot`);
```
Or run with `--heapsnapshot-signal=SIGUSR2` and send that signal to the process. Warning: taking a snapshot pauses the process and can need roughly 2x the heap in extra memory. Do not do it on an instance that is close to its limit, and take it out of the load balancer first.

## Step 4: Diff the snapshots

1. In DevTools, load Snapshot 3, pick "Comparison" from the dropdown (not "Summary"), and compare against Snapshot 2 (then also against 1).
2. Sort by "# Delta" (count growth) and "Size Delta".
3. Focus on constructors with a large positive delta that match the number of requests you sent. If you sent 1,000 requests and see +1,000 `Object`, `Closure`, `Promise`, `Socket`, or a custom class, that is a per-request leak.
4. Ignore noise at the top: `(compiled code)`, `(system)`, `(string)` and `(array)` deltas are often by-products. Look for your own class names and for concatenated or sliced strings that are being retained.
5. Also check "Summary" view sorted by "Retained Size" in Snapshot 3 to find the largest retention overall.

## Step 5: Find the retainer chain

This is the step that tells you why the objects are not collected.

1. Click one leaked object in the diff list.
2. Open the "Retainers" pane below. It shows the chain of references from a GC root to the object.
3. Read it from the bottom up: the bottom is the root (a global, module-level variable, a timer, a socket), the top is your object.
4. Note the "distance" column: a small distance means it is reachable from something close to a root.
5. Identify the single reference you control. Typical culprits are shown in Step 6.
6. Use the object's property names and the closure's `context` entries to locate the source line. In the Retainers pane, "Shortcut" and "context" entries point at closures; clicking the function name links to the source location.

## Step 6: Recognize the usual causes

| Cause | What it looks like in the retainers | Fix |
|---|---|---|
| Unbounded cache/Map/array/object used as a cache | Module-level `Map` or array with growing entries | Use an LRU with a max size and TTL (`lru-cache`), or `WeakMap` if keys are objects |
| Event listeners never removed | `EventEmitter._events` holding closures; `MaxListenersExceededWarning` in logs | `removeListener`/`off`, use `once`, or `AbortSignal`; never add a listener per request on a long-lived emitter |
| Timers never cleared | `Timeout` objects retaining closures | `clearInterval`/`clearTimeout`, `timer.unref()` where appropriate |
| Closures capturing large scope | Closure context holding big arrays, request/response objects | Null out references, avoid capturing whole `req`/`res`, extract only the needed fields |
| Globals created by accident | Properties on `globalThis` | Use strict mode and lint (`no-undef`) |
| Unresolved promises or growing promise chains | Many pending `Promise` objects | Add timeouts, always settle or reject, avoid infinite `then` chains |
| Streams not consumed or destroyed | `ReadableState`, `Socket`, buffered chunks | Use `pipeline()`, handle `error`/`close`, call `destroy()`, apply backpressure |
| Unclosed resources | Many DB connections, HTTP agents, sockets, file handles | Pool and reuse; close in `finally` |
| Per-request data in module scope | Request-keyed entries in a global map | Delete on completion, or use `AsyncLocalStorage` and let it scope itself |
| Logging/metrics with unbounded labels | Prometheus label cardinality growth, per-user metric objects | Bound the label values |
| Memoization/dedup without eviction | Memo tables keyed by input | Bound the memo size |
| Third-party library leaks | Retainers go into `node_modules` | Check the issue tracker, upgrade or pin, or replace |

## Step 7: Leaks outside the JS heap

If `heapUsed` is flat but `rss` climbs:

1. Check `external` and `arrayBuffers` in `process.memoryUsage()`. Growth means Buffers are retained (large `Buffer.alloc`, unconsumed streams, retained slices of big Buffers; a small `.slice()` of a large Buffer keeps the whole backing store alive).
2. Check native addons (image processing, crypto, DB drivers) and whether you call their `close()`/`free()` APIs.
3. Use `--heap-prof` or `--trace-gc` to see if GC is happening at all.
4. Run with `perf`/`heaptrack`/`valgrind --tool=massif` or `jemalloc` profiling for native allocations.
5. Test `MALLOC_ARENA_MAX=2` (glibc fragmentation is a frequent false "leak" in containers).
6. Count open handles: `process._getActiveHandles().length` and `process._getActiveRequests().length` are quick indicators for sockets and timers not being released.

## Step 8: Allocation timeline and sampling (finding where objects are created)

Snapshots show what is retained. To find where it was allocated:

1. In DevTools Memory tab choose "Allocation instrumentation on timeline". Run your load. Blue bars are allocations still alive; select a bar to see only those objects and their allocation stack traces.
2. Choose "Allocation sampling" for a lower-overhead view of allocation call stacks. It is light enough for staging and brief production use.
3. Alternatively, `node --heap-prof app.js` writes a `.heapprofile` file you can open in DevTools.
4. Other tools worth knowing: `clinic.js` (`clinic heapprofiler`, `clinic doctor`), `memlab` (automates the snapshot-diff flow and flags leaked objects), `heapdump`, and `@datadog/pprof` or Pyroscope for continuous profiling in production.

For production specifically:
- Take one instance out of rotation, then snapshot it. Do not snapshot a pod that is serving traffic and near its memory cap.
- Compare two snapshots from the same process separated by a long enough interval to show growth.
- If the process was OOM-killed, run with `--heapsnapshot-near-heap-limit=3` to dump snapshots as it approaches the limit, and keep core dumps/`--report-on-fatalerror` enabled.

## Step 9: Fix it

1. Make the smallest change that removes the retaining reference (bound the cache, remove the listener, clear the timer, destroy the stream).
2. Prefer structural fixes over patches: a bounded LRU instead of a manually pruned Map; `pipeline()` instead of manual `pipe()`; `AbortController` for cancellation.
3. Add a guardrail where it makes sense: `emitter.setMaxListeners`, cache size metrics, request timeouts.

## Step 10: Verify the fix

1. Repeat the exact load from Step 2 with the fixed build.
2. Repeat the three-snapshot comparison. The suspect constructor should show no growing delta.
3. Watch `heapUsed` over a long run (an hour or more under steady load). The post-GC floor should be flat.
4. Add a regression test or CI soak check. A simple one: run N iterations of the code path, force GC with `node --expose-gc` and `global.gc()`, then assert that `heapUsed` growth stays under a threshold. Use `WeakRef` plus `FinalizationRegistry`, or `memlab` scenarios, for object-level assertions.
5. Keep memory dashboards and an alert on the post-GC heap trend (not raw RSS) so a recurrence is caught early.

## Quick checklist

1. Plot `heapUsed`, `rss`, `external` over hours and confirm the floor rises.
2. Reproduce locally with `--inspect` and load.
3. Warm up, GC, snapshot; load, GC, snapshot; load, GC, snapshot.
4. Compare snapshots, sort by delta, match counts to request counts.
5. Read the retainer chain to the root.
6. Fix the reference; verify with a repeat run.
7. Add monitoring and a regression check.
