# Hunting Down a Memory Leak in a Node.js Service: The Complete Walkthrough

This guide goes from "I think something is leaking" to "the fix is verified in production". Each step says what to do, why you do it, what you should see, and what can go wrong. Read it once end to end, then use it as a checklist.

---

## Step 0: Understand what you are hunting

### How Node.js uses memory

A Node process has several memory regions. You need to know which one is growing, because the tools and fixes differ.

- **RSS (resident set size):** all physical memory the OS has given the process. It includes everything below.
- **V8 heap (`heapTotal` / `heapUsed`):** where JavaScript objects live: strings, closures, arrays, Maps, class instances. Most leaks you will find are here.
- **External memory (`external`):** memory for C++ objects tied to JS objects, such as Buffers, some native bindings, and zlib streams.
- **ArrayBuffers (`arrayBuffers`):** backing stores for Buffers and typed arrays. This is a subset of external.
- **Native / off-heap memory:** native addons, OpenSSL, libuv handles, and the allocator's own overhead. The V8 heap profiler cannot see it.
- **Code and stack:** JIT-compiled code and thread stacks. These are usually small.

### Leak versus normal behavior

Not every rising memory graph is a leak.

- **Garbage collection is lazy.** V8 lets garbage pile up and collects it when it needs to. A sawtooth pattern (up, then a sharp drop) is healthy.
- **Warm-up growth is normal.** Caches fill, JIT code is generated, and connection pools open. Memory grows for the first minutes or hours and then plateaus.
- **The heap limit scales with the machine or container.** Node will happily use a large share of what it is allowed before collecting aggressively.
- **A real leak** shows up as a rising floor. The memory level right after each major GC keeps climbing, and the trend is roughly proportional to traffic or time. It ends in an out-of-memory crash, an OOM kill by the OS or orchestrator, or a GC-thrashing service whose latency climbs.

### The core idea

A JavaScript leak is always the same thing: **objects that are no longer needed are still reachable from a GC root.** The collector only frees unreachable objects, so something is holding a reference. Your job is to find what holds it. Everything below is a method for finding that reference chain.

## Step 1: Confirm there is a leak and classify it

Before you take a single heap snapshot, collect evidence.

### 1a. Look at your existing monitoring

Check your metrics system (Prometheus, Datadog, CloudWatch, Grafana, and so on) for:

- Container or process memory over several days.
- Restarts or OOM kills (`OOMKilled` in Kubernetes, or `Out of memory: Killed process` in `dmesg`).
- Whether memory correlates with traffic, a deploy, or a specific endpoint or job.
- Whether it resets on deploy or restart. That tells you it is process-local state, not something external.

Write down: when it started, what changed around then, how fast it grows, and whether it is per-instance or fleet-wide.

### 1b. Expose in-process memory metrics

If you do not have them, add a periodic log or metric. This is the single most useful thing to add:

```js
const v8 = require('node:v8');

setInterval(() => {
  const m = process.memoryUsage();
  const h = v8.getHeapStatistics();
  console.log(JSON.stringify({
    t: new Date().toISOString(),
    rssMB: +(m.rss / 1048576).toFixed(1),
    heapUsedMB: +(m.heapUsed / 1048576).toFixed(1),
    heapTotalMB: +(m.heapTotal / 1048576).toFixed(1),
    externalMB: +(m.external / 1048576).toFixed(1),
    arrayBuffersMB: +(m.arrayBuffers / 1048576).toFixed(1),
    heapLimitMB: +(h.heap_size_limit / 1048576).toFixed(1),
    nativeContexts: h.number_of_native_contexts,
    detachedContexts: h.number_of_detached_contexts,
  }));
}, 30_000).unref();
```

`unref()` keeps this timer from holding the process open.

If you use `prom-client`, `collectDefaultMetrics()` gives you `nodejs_heap_size_used_bytes`, `nodejs_external_memory_bytes`, `process_resident_memory_bytes`, and GC duration metrics for free.

### 1c. Classify the growth

Read the numbers like this:

| What grows | Likely cause |
|---|---|
| `heapUsed` climbs, `external` flat | A JS-object leak: caches, closures, listeners, global arrays. This is the most common case. |
| `external` / `arrayBuffers` climbs | Buffer leak: streams not consumed or destroyed, large Buffers retained, native bindings. |
| `rss` climbs, but `heapUsed` and `external` are flat | Native addon leak, allocator fragmentation, too many threads or handles, or memory that was freed but not returned to the OS. |
| `heapUsed` is flat after GC but `rss` oscillates high | Fragmentation or lazy return of memory to the OS. Usually not a true leak. |
| `heapUsed` climbs and `detachedContexts` climbs | Leaking `vm` contexts or iframes (rare on servers). |

### 1d. Turn on GC tracing for a quick check

Run with `--trace-gc` for a while:

```bash
node --trace-gc server.js
```

Look at the lines containing `Mark-Compact` (full GCs). Each shows memory before and after, for example `120.4 (150.2) -> 118.9 (151.0) MB`. If the "after" value after each full GC keeps climbing, you have a leak. If it drops back to a stable baseline, you do not.

### 1e. Check the heap limit

Know your ceiling:

```bash
node -e "console.log(require('v8').getHeapStatistics().heap_size_limit/1048576)"
```

If your container limit is smaller than V8's heap limit, the OS will kill you before V8 throws. Set `--max-old-space-size` to roughly 75 to 80 percent of the container memory limit. Otherwise a "leak" can be just an under-sized heap setting.

## Step 2: Reproduce it in a controlled environment

Debugging in production is possible, and we will cover it later, but a local or staging reproduction is faster and safer.

### 2a. Run the service with inspector and GC exposure enabled

```bash
node --inspect --expose-gc server.js
```

- `--inspect` opens the debugger on port 9229, bound to localhost by default.
- `--expose-gc` gives you `global.gc()` so you can force a full collection and rule out lazy-GC noise.

Never expose the inspector port to a network you do not fully trust. It grants arbitrary code execution.

### 2b. Generate load that resembles production

Pick a load tool such as `autocannon`, `k6`, `wrk`, `artillery`, or a script of your own:

```bash
npx autocannon -c 50 -d 120 http://localhost:3000/api/orders
```

Use realistic payloads, distinct users or IDs (a cache keyed by user ID only leaks if the keys vary), and a mix of endpoints.

### 2c. Bisect to the leaking path

If you do not know which endpoint leaks:

1. Hit one endpoint at a time for a few minutes each.
2. After each run, force a GC and read `heapUsed`.
3. The endpoint whose post-GC `heapUsed` rises and stays up is your suspect.

To force GC and read the baseline, add a debug-only route or signal handler:

```js
process.on('SIGUSR2', () => {
  global.gc?.();
  const m = process.memoryUsage();
  console.log('post-GC heapUsed MB', (m.heapUsed / 1048576).toFixed(1));
});
```

Then run `kill -USR2 <pid>`. Note that Node's own inspector uses `SIGUSR1`, so use a different signal.

### 2d. Make it fail faster (optional)

Run with a small heap so the leak shows up in minutes rather than days:

```bash
node --max-old-space-size=128 --expose-gc server.js
```

This is a good trick for reproducing, but do not use it to judge the production heap size.

## Step 3: Take heap snapshots with the three-snapshot technique

This is the standard approach, and it works because it separates real leaks from noise.

### 3a. Connect DevTools

1. Start the service with `--inspect`.
2. Open Chrome and go to `chrome://inspect`.
3. Under "Remote Target", click **inspect** on your Node process. (Alternatively, click "Open dedicated DevTools for Node".)
4. Open the **Memory** tab.
5. Select **Heap snapshot** and leave "Take snapshot" selected.

Taking a snapshot **pauses your process**, and it can take seconds to minutes on large heaps. It also needs roughly 1.5 to 2 times the heap size in additional memory. Do not do this casually on a loaded production instance.

### 3b. The procedure

1. **Warm up.** Send a few hundred or thousand requests so lazy initialization is done, caches are primed, and JIT is warm.
2. Click the trash-can icon in the Memory tab to force a GC. (Or call `global.gc()`.) Take **Snapshot 1**.
3. Run the suspect workload. Use a fixed, countable number of operations, for example exactly 1,000 requests to the suspect endpoint.
4. Force GC again and take **Snapshot 2**.
5. Run the **same** workload again (another 1,000 requests).
6. Force GC and take **Snapshot 3**.

Why three? Anything that is allocated once during the first run (module caches, lazy singletons, initialized pools) appears in the diff between 1 and 2 but not between 2 and 3. A real leak keeps growing in every interval.

### 3c. Compare the snapshots

1. Select **Snapshot 3**.
2. Change the view dropdown from "Summary" to **"Objects allocated between Snapshot 1 and Snapshot 2"**. (In some versions: Select the snapshot, then use the "Comparison" view and choose a base snapshot.)
3. Use Comparison view with Snapshot 2 as the base, and sort by **# Delta** or **Size Delta**, descending.
4. Look for constructor names whose count grows by roughly the number of operations you ran, or a clean multiple of it. If you made 1,000 requests and see +1,000 `RequestContext` objects, +1,000 `Closure`s, or +1,000 `Buffer`s, that is your leak.

### 3d. Read the columns

- **Shallow size:** the memory held by the object itself.
- **Retained size:** the memory that would be freed if this object were deleted, including everything only reachable through it. This is usually the number that matters.
- **Distance:** the shortest path length from a GC root. A big distance means it is buried; a small distance means it is held close to the root.

### 3e. Filter out noise

Common entries that look scary but are usually not leaks:

- `(compiled code)`, `(system)`, `(string)` and `(array)` totals. Dig into what holds them, not the totals.
- Growth in `(concatenated string)` or `(sliced string)`. These are V8 string internals. The real culprit is usually whatever holds the string.
- A small, one-time increase between Snapshot 1 and Snapshot 2 that is gone in the next interval.

## Step 4: Find what is holding the objects (the retainers)

Once you have a suspect constructor, find out why it is not collected.

1. In the snapshot, click the suspect class and expand it to see individual instances.
2. Click one instance. Look at the **Retainers** panel at the bottom.
3. Read the chain from the bottom up. Each row says "this object is referenced by that property of the next." For example:

```
RequestContext @12345
  context in system / Context @777
    listener in (array) @555
      _events in EventEmitter @321
        emitter in global.metricsBus (Window / global)
```

This reads: the global `metricsBus` emitter holds an array of listeners, one of which closes over a `RequestContext`. Every request adds a listener and none is removed.

4. Ignore weak references (shown in grey or labeled `weak`); they do not keep objects alive.
5. Check several instances. If their retainer chains differ, there may be more than one leak.
6. Use the retainer chain to find the code. Closure rows often show the function name and a source location. Click it to jump to the file and line.

If the chain ends at something unhelpful like `system / Context`, that is a closure scope. Look for functions defined in the scope that hold large variables (see the closure section below).

---

## Step 5: Use allocation tracking to find where the objects were created

Retainers tell you who holds the object. Allocation tracking tells you who created it.

### Allocation instrumentation on timeline

1. In the Memory tab, choose **Allocation instrumentation on timeline** and start recording.
2. Run the workload.
3. Stop recording. Blue bars on the timeline are allocations that are still alive; grey bars were freed.
4. Select a time range with persistent blue bars. The constructor list below shows what was allocated and survived.
5. Click an object to see the **allocation stack trace**, the call stack where it was created.

This directly points at the line of code that allocated the leaked object. It slows the process down considerably, so use it in a test environment.

### Allocation sampling

If instrumentation is too slow, **Allocation sampling** has low overhead and gives a statistical view of which functions allocate the most live memory. It is acceptable for a moderately loaded staging box. It reports allocations by call site and is not as precise as instrumentation, but it can be used for longer runs.

## Step 6: Know the usual suspects and check each one

Most leaks are one of the following. Compare what you found in the retainer chains against this list.

### 6a. Unbounded caches and in-memory maps

```js
const cache = new Map();
app.get('/user/:id', async (req, res) => {
  if (!cache.has(req.params.id)) cache.set(req.params.id, await loadUser(req.params.id));
  res.json(cache.get(req.params.id));
});
```

Nothing ever evicts entries. Fixes:

- Use an LRU with a maximum size and TTL, such as `lru-cache`.
- Use `WeakMap` or `WeakRef` when keys are objects whose lifetime should control the entry.
- Cap the size explicitly and emit a metric for the size.

### 6b. Event listener accumulation

```js
function handle(req) {
  globalBus.on('update', () => doThing(req));   // never removed
}
```

Node warns with `MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 listeners added`. **Do not silence this by raising the limit.** It is usually a true signal. Fixes:

- Pair every `on` with an `off` or `removeListener`, typically in a `finally` block or on a `close` event.
- Use `once` when you only need one event.
- Use `AbortSignal` with `events.on` or `addEventListener` for automatic cleanup.

To debug, print `emitter.listenerCount('eventName')` over time, or run with `--trace-warnings` to see where the warning originated.

### 6c. Closures that capture too much

A closure keeps alive everything in its enclosing scope that any closure in that scope references. In V8, all closures created in the same scope share a context object, so a small, long-lived callback can accidentally keep a huge object alive:

```js
function process(bigPayload) {
  const summary = summarize(bigPayload);
  longLivedRegistry.push(() => summary.id);   // may retain bigPayload via shared context
}
```

Fixes: extract the needed values first, then create the callback in a small separate function that closes over only those values. Set large variables to `null` when finished if they live in a shared scope.

### 6d. Global variables and accidental globals

```js
function f() { results = []; }  // forgot "let", creates global in sloppy mode
```

Use `'use strict'` or ES modules, which are strict by default. Use ESLint's `no-undef` and `no-implicit-globals`. Also look for module-level arrays and objects that are appended to but never trimmed (request logs, metrics buffers, "recent errors" lists).

### 6e. Timers and intervals never cleared

```js
setInterval(() => poll(conn), 1000);   // keeps conn and everything it references alive forever
```

Store the handle and call `clearInterval` on shutdown or when the owning object is disposed. A `setTimeout` chain that reschedules itself has the same issue.

### 6f. Promises that never settle, and unbounded queues

A promise that never resolves, together with its `.then` callbacks, stays in memory while anything holds it. A queue (for example an in-memory job queue or a stream with no backpressure) that is fed faster than it is drained grows without bound. Look at:

- Streams where you ignore `write()` returning `false`. Respect backpressure and wait for `'drain'`.
- `Promise.all` over unbounded input. Use a concurrency limiter.
- Awaiting something that has no timeout. Add `AbortSignal.timeout(...)`.

### 6g. Streams and sockets not destroyed

If a client disconnects mid-response and you never call `destroy()` on the source stream, file descriptors and buffers stay allocated. Use `stream.pipeline()` (or `stream/promises.pipeline`), which destroys all streams on error or close. Listen for `req.on('close')` / `res.on('close')` and cancel upstream work.

### 6h. HTTP clients and agents

Creating a new `http.Agent` or client instance per request without keep-alive limits, or never consuming a response body (`undici`/`fetch`), keeps sockets and buffers alive. Always consume or cancel response bodies, and reuse a single agent/client.

### 6i. Per-request state stored on long-lived objects

Things like `AsyncLocalStorage` stores, request-ID maps, and "in-flight requests" tables that are added to on entry and not removed on all exit paths (error, timeout, abort). Use `try/finally`.

### 6j. Logging, tracing and monitoring libraries

APM agents, tracing spans that are never ended, and loggers that buffer when their transport is down all leak in practice. Check by disabling them in a test run and seeing whether the growth stops.

### 6k. Memoization and `require` cache

`memoize(fn)` with unbounded argument keys is a cache. Dynamic `require()` of generated paths adds permanently to `require.cache`. Dynamic `import()` of unique URLs does the same for the module map.

### 6l. Large strings that are sliced

A tiny substring may retain the whole parent string in some cases. If you keep small slices of huge strings (for example parsed log lines), copy them (for example with `Buffer.from(str).toString()` or by flattening) so the parent can be freed.

### 6m. Native addons and Buffers

If `heapUsed` is flat but `rss` or `external` grows, check native modules (image processing, database drivers, crypto, compression). Look at their issue trackers for known leaks, pin or upgrade versions, and make sure you call any `.close()`, `.destroy()`, or `.free()` methods they require.

## Step 7: Investigate when the heap profiler cannot see it (off-heap / RSS-only growth)

If `heapUsed` is flat and `rss` climbs:

1. **Check `external` and `arrayBuffers`.** If they climb, find which code allocates Buffers (`Buffer.alloc`, file reads, network payloads, compression) and who retains them.
2. **Check the number of handles and threads.**
   ```js
   console.log(process.getActiveResourcesInfo?.());
   ```
   Many `TCPSocketWrap`, `Timeout`, `FSReqCallback` entries suggest leaked handles. On Linux, `ls /proc/<pid>/fd | wc -l` counts file descriptors, and `ls /proc/<pid>/task | wc -l` counts threads.
3. **Look at the allocator.** Linux glibc malloc can fragment under Node's workload and not return memory to the OS. Two common mitigations:
   - Set `MALLOC_ARENA_MAX=2` in the environment.
   - Use `jemalloc` (via `LD_PRELOAD`), which often shows a flatter RSS.
   If RSS stabilizes after this change, it was fragmentation, not a leak.
4. **Profile native memory.** Use `heaptrack`, `valgrind --tool=massif`, or `jemalloc`'s profiling (`MALLOC_CONF=prof:true,...` with `jeprof`) to see which native code allocates the memory.
5. **Bisect the dependency tree.** Disable native modules one by one in a test build and watch RSS.

## Step 8: Use additional tooling when DevTools is not enough

- **Clinic.js** (`npx clinic doctor -- node server.js`, and `clinic heapprofiler`) gives a guided analysis and flame graphs for allocations.
- **`heapdump` / `v8.writeHeapSnapshot()`** lets you write a `.heapsnapshot` file from code so you can analyze it elsewhere:
  ```js
  const v8 = require('node:v8');
  process.on('SIGUSR2', () => {
    const file = v8.writeHeapSnapshot();   // writes Heap.<date>.<pid>.heapsnapshot in cwd
    console.log('wrote', file);
  });
  ```
  Load the file in Chrome DevTools: Memory tab, then "Load".
- **`--heapsnapshot-signal=SIGUSR2`** is a built-in Node flag that writes a snapshot when the signal arrives, with no code change.
- **`--heapsnapshot-near-heap-limit=3`** automatically writes snapshots as the process approaches its heap limit, which captures the state just before an OOM.
- **`--heap-prof`** writes a sampling heap profile (`.heapprofile`) at exit, which you can load into DevTools.
- **`node:perf_hooks`** `PerformanceObserver` for `'gc'` entries tells you how long and how often GC runs.
- **`memlab`** (from Meta) automates the leak-finding procedure with scenario scripts and is good for regression tests.
- **`WeakRef` and `FinalizationRegistry`** can be used in tests to assert that an object *does* get collected after you drop it. Treat them as diagnostic tools, not as program logic.

## Step 9: Debugging in production safely

Sometimes you cannot reproduce locally. Do this carefully.

1. **Pick one instance** and take it out of rotation (drain traffic) before taking a snapshot. Snapshotting pauses the event loop and can fail health checks and trigger restarts.
2. **Make sure there is headroom.** Snapshot writing needs extra memory. If the process is already near its container limit, the snapshot itself can OOM it. Raise the limit temporarily on that instance if you can.
3. **Take two snapshots** separated by a period of load (for example 30 minutes), rather than three, if the cycle is long. Compare them in DevTools. Also take one right after startup as a baseline.
4. **Use `--heapsnapshot-near-heap-limit`** so you capture the state when the process is nearly full, even if you were not watching.
5. **Treat snapshots as sensitive data.** They contain everything in memory: tokens, passwords, user data, session cookies. Store them encrypted, restrict access, and delete them after use.
6. **Copy the file off the box** and analyze it on your workstation. Large snapshots (multi-GB) may need a machine with a lot of RAM, and you may need to run DevTools with a larger memory allowance.
7. **Run a canary** with extra instrumentation (for example a 5-minute allocation sampling profile) rather than the whole fleet.

## Step 10: Form a hypothesis, then prove it before fixing

Do not change code on a hunch. For each candidate:

1. State the hypothesis: "Each request registers a listener on `metricsBus` that is never removed."
2. Predict what you would see: "`metricsBus.listenerCount('update')` increases by 1 per request."
3. Measure it: log the count, or find it in the snapshot as a growing array.
4. If the data matches, you have confirmed the cause. If not, return to Step 3 or 4 with the new information.

Write a small isolated reproduction (a script that calls the suspect function in a loop, forces GC, and prints `heapUsed`). It becomes your regression test:

```js
// leak-test.js — run with: node --expose-gc leak-test.js
const { handleRequest } = require('./handler');

async function run(n) { for (let i = 0; i < n; i++) await handleRequest(fakeReq(i)); }

(async () => {
  await run(2000);          // warm up
  global.gc(); const a = process.memoryUsage().heapUsed;
  await run(20000);
  global.gc(); const b = process.memoryUsage().heapUsed;
  const growthMB = (b - a) / 1048576;
  console.log('growth MB:', growthMB.toFixed(2));
  if (growthMB > 5) { console.error('LEAK SUSPECTED'); process.exit(1); }
})();
```

## Step 11: Fix it

Pick the narrowest correct fix:

- **Unbounded cache:** bound it (LRU, TTL, max size) or remove it.
- **Listener leak:** remove the listener on the right lifecycle event, or restructure so there is one listener that dispatches.
- **Closure capture:** copy only the needed values and avoid capturing large objects.
- **Timer:** clear it on teardown.
- **Stream/socket:** use `pipeline`, handle `close`/`error`, and destroy resources.
- **Queue:** add backpressure, a maximum length, and a rejection or drop policy.
- **Global state:** move per-request state into request scope, and clean up in `finally`.
- **Native/dependency:** upgrade, patch, replace, or work around by recycling.

Add a metric for whatever structure was leaking (cache size, listener count, queue depth) so you can see it regress.

---

## Step 12: Verify the fix

1. Re-run your isolated leak test. Post-GC `heapUsed` should be flat.
2. Re-run the load test and the three-snapshot comparison. The suspect constructor should no longer show a delta proportional to the operations.
3. Soak test in staging for longer than the original time-to-failure feels like it needs, ideally at least several hours at realistic load. Watch the post-GC floor, not the peaks.
4. Deploy to a canary in production. Compare its memory curve with the unpatched instances over 24 hours or more.
5. Roll out gradually, and confirm the fleet-wide graph flattens.
6. Keep an alert on a rising post-GC heap floor or on memory growth rate, so a future leak is caught in hours, not weeks.

---

## Step 13: Mitigate while you investigate

If the service is hurting users right now, buy time without hiding the problem:

- Schedule rolling restarts (for example, a Kubernetes liveness check based on memory or a max-lifetime for workers).
- Use cluster or PM2 with `max_memory_restart` so workers are recycled gracefully before they hit the limit.
- Set `--max-old-space-size` appropriately so that Node fails with a clear error and a heap snapshot (`--heapsnapshot-near-heap-limit`) rather than being SIGKILLed with no data.
- Add capacity or lower per-instance concurrency.

These are stopgaps. They make an incident survivable, but the leak is still there.

---

## Step 14: Prevent the next one

- Lint for accidental globals, unhandled promises, and floating listeners.
- Code-review any new in-memory cache, queue, or `on(...)` call with the question "what removes this?"
- Treat `MaxListenersExceededWarning` as an error in CI.
- Add a soak test or `memlab` scenario to CI for critical paths.
- Export memory, GC, listener-count, and queue-depth metrics by default, with dashboards and alerts.
- Prefer bounded data structures by default.
- Run with `--heapsnapshot-near-heap-limit` in production so you always get evidence on failure.

---

## Quick checklist

1. Is the post-GC floor rising? (`--trace-gc`, metrics.) If not, it is not a leak.
2. Which region grows: heap, external, or RSS only?
3. Reproduce with load locally; bisect endpoints.
4. Warm up, then take three snapshots with a fixed workload between them, forcing GC before each.
5. Compare snapshots by delta count; find the constructor that grows with the workload.
6. Follow the retainer chain to the root.
7. Use allocation timeline or sampling to find where the objects are created.
8. Check the usual suspects: caches, listeners, closures, timers, streams, queues, globals.
9. Off-heap growth: check Buffers, handles, native modules, allocator settings.
10. Prove the hypothesis with a small isolated test.
11. Fix the narrowest cause and add a metric.
12. Verify with a leak test, a soak test, and a canary.
13. Add monitoring and guards so it cannot silently return.
