A TLS handshake establishes an encrypted channel by having client and server agree on protocol version, cipher suite, and shared keys before any application data flows. The client sends a ClientHello with supported TLS versions, cipher suites, and a random nonce; the server replies with ServerHello selecting the cipher suite, its own random nonce, and its certificate (containing its public key, signed by a CA). In TLS 1.2, the client verifies the certificate chain, generates a pre-master secret, encrypts it with the server's public key, and sends it over; both sides then derive the same master secret and session keys from the two randoms and pre-master secret. TLS 1.3 instead uses ephemeral Diffie-Hellman (ECDHE) key shares exchanged in the first round trip, deriving keys immediately and encrypting the certificate and remaining handshake messages — cutting the handshake to one round trip instead of two. Both sides send a Finished message, a MAC over the entire handshake transcript, to confirm integrity and prevent tampering/downgrade attacks. Once Finished messages are verified, both switch to symmetric encryption (e.g., AES-GCM or ChaCha20-Poly1305) using the derived session keys for all subsequent application data.
