Use REST for this. GraphQL's advantages don't have anything to grab onto at this scale, and it would add real overhead you don't need:

**Why REST fits better here:**
- **Three endpoints is REST's sweet spot.** Resource-oriented CRUD (`GET/POST/PUT/DELETE` on a resource) maps directly onto HTTP semantics — you get status codes, caching, and idempotency semantics for free.
- **One team, one client mental model.** GraphQL earns its keep when multiple heterogeneous clients (web, mobile, third parties) need different slices of data and you want to avoid over/under-fetching or endpoint sprawl. With one team and three endpoints, there's no fetching mismatch to solve.
- **Lower operational overhead.** No schema-definition layer, no resolver setup, no N+1 query concerns to guard against, no need to think about query complexity/depth limiting. Standard HTTP tooling (curl, browser devtools, load balancers, API gateways, logging) all work without adaptation.
- **Simpler debugging and monitoring.** Errors are ordinary HTTP status codes; you can alert on 5xx rates per route out of the box. GraphQL typically returns 200 OK with errors nested in the response body, which complicates monitoring for a service this small.
- **Caching is trivial.** GET requests cache naturally via HTTP semantics (ETags, `Cache-Control`). GraphQL, usually served over POST, needs extra work to get equivalent caching.

**When you'd reconsider:** if this grows into dozens of endpoints with deeply nested/relational data, or multiple consumer teams start requesting different shapes of the same data and you're tempted to bolt on query params like `?include=foo,bar` everywhere — that's the point where GraphQL's flexibility starts paying for its complexity. For three endpoints behind one team, that day is far off; adding GraphQL now would be solving a problem you don't have yet.
