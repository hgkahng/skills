## Restating your question

You're building a small, internal CRUD (create/read/update/delete) service — used by a single team, exposing only three endpoints — and you want to know whether REST or GraphQL is the better architectural choice for the API layer.

## Reasoning through the decision

### Step 1: Identify what actually differentiates REST from GraphQL

The two approaches solve overlapping but distinct problems:

- **REST** models an API as a set of resources, each with a URL, manipulated via standard HTTP verbs (GET, POST, PUT/PATCH, DELETE) and status codes. Its main strengths are simplicity, ubiquity of tooling, and alignment with HTTP semantics (caching, status codes, content negotiation).
- **GraphQL** models an API as a single endpoint backed by a typed schema, where clients specify exactly which fields and relationships they want in a query. Its main strengths are (a) avoiding over-fetching/under-fetching when data shapes are complex or nested, and (b) letting many different client types (web, mobile, third-party) each pull a custom shape of data without the backend team having to build bespoke endpoints for each.

So the real question is: does this project have the kind of complexity that GraphQL's strengths address?

### Step 2: Apply the criteria that actually matter to your scenario

**Number and diversity of consumers.** GraphQL earns its keep when you have multiple, independently-evolving client teams (web, iOS, Android, partner integrations) that each want different slices of the same data, and you don't want the backend team to be a bottleneck for every UI change. You have one team. There's no cross-team coordination problem to solve, and no divergent consumer needs to reconcile.

**Surface area / data complexity.** GraphQL shines when the domain graph is deep — many entity types with nested relationships (e.g., a user has orders, each order has line items, each line item has a product, each product has reviews...) where a REST approach would require either many round trips or bloated "kitchen sink" endpoints. Three CRUD endpoints is about as flat and simple as an API gets. There's essentially no over-fetching problem to solve because there isn't a complex object graph to traverse.

**Operational overhead.** GraphQL requires a schema definition, a resolver layer, usually a dedicated server library (Apollo Server, GraphQL Yoga, etc.), and awareness of pitfalls like the N+1 query problem (typically solved with DataLoader-style batching). It also complicates the parts of the stack that assume REST semantics: HTTP caching (GraphQL is usually a single POST endpoint, so you lose free caching via ETags/Cache-Control unless you add persisted queries or a caching layer), API gateways, rate limiting per-resource, and even basic request logs (every request hits the same URL, so distinguishing "which operation failed" requires parsing the query body rather than reading the path). For three endpoints, all of this is pure overhead with no offsetting benefit.

**Debuggability and tooling.** REST maps naturally onto things every engineer already knows: curl, Postman, browser dev tools, standard HTTP status codes for errors (404, 400, 409, etc.). GraphQL typically returns 200 OK even on business-logic errors, with error detail buried in the response body — which is a well-known source of monitoring/alerting friction. For an internal tool that a small team will maintain, minimizing "surprise" is valuable.

**Growth trajectory.** The one scenario where I'd revisit this is if you expect the service to grow substantially — many more resources, deep relationships, or multiple consumer teams within the next year. But "simple internal CRUD service" reads as a description of steady-state scope, not a stepping stone to a large platform.

### Step 3: Alternatives I considered and rejected

- **gRPC**: Better suited to high-performance, polyglot service-to-service communication with strict contracts (via Protocol Buffers) and streaming needs. It adds code-generation tooling and a binary format that's harder to poke at with a browser or curl. For an internal CRUD service with three endpoints, this is more machinery than the problem warrants, and it sacrifices human-readability for performance you likely don't need.
- **tRPC** (if your stack is TypeScript end-to-end): This is actually a reasonable dark-horse alternative — it gives you end-to-end type safety between client and server without writing a schema definition language, and it's lighter-weight than GraphQL. I considered recommending it, but it only makes sense if both client and server are TypeScript; absent that detail, and given that plain REST already solves your problem with even less machinery, I didn't want to introduce a stack-specific dependency you didn't ask about.
- **Plain RPC-style JSON-over-HTTP** (single `/api` endpoint with an action parameter): Rejected because it throws away the free benefits of REST (HTTP verbs, status codes, cacheability) without gaining anything GraphQL would give you either. It's strictly worse than REST for this use case.

### Step 4: Arrive at a recommendation

Given one team and three endpoints, none of GraphQL's core value propositions (flexible field selection for divergent clients, avoiding deep-graph over-fetching, decoupling frontend iteration from backend releases) apply, while all of its costs (schema/resolver layer, N+1 handling, harder caching, less standard error semantics, more moving parts to maintain) are still fully present. REST is the conventional, lower-friction choice and is very likely the right one here.

## Summary and next steps

**Recommendation: use REST.** For a single-team, three-endpoint internal CRUD service, GraphQL's benefits don't apply at this scale, and it would add schema/resolver overhead, N+1 query risk, and more awkward caching and error handling for no real gain. REST gives you simplicity, ubiquitous tooling, and natural alignment with HTTP semantics — exactly what a small internal tool needs.

Practical next steps if you go with REST:
1. Model your three endpoints as resources with standard verbs (e.g., `GET/POST /widgets`, `GET/PUT/DELETE /widgets/{id}`) rather than RPC-style action names.
2. Write a lightweight OpenAPI/Swagger spec — even for an internal service, it gives you free documentation and client-generation if you ever need it.
3. Use standard HTTP status codes consistently (200/201/204 for success, 400/404/409/422 for client errors) so debugging stays intuitive.
4. Revisit this decision only if you start seeing: multiple independent consumer teams with different data needs, a rapidly growing/deeply nested data model, or a strong need for clients to shape their own queries. If those appear, GraphQL becomes worth the added complexity — but that's a "grow into it" decision, not a starting point.
