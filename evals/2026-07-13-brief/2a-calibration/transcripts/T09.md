**Restating the question:** You're asking two related things — (1) which TCP port PostgreSQL listens on out of the box, and (2) whether it's a good idea to configure your firewall/network so that port is reachable from any host on the internet, rather than only from trusted/internal machines.

**Step 1: The default port**

PostgreSQL listens on **TCP port 5432** by default. This is set by the `port` parameter in `postgresql.conf` and is the port IANA has registered for PostgreSQL. It's worth double-checking you're not conflating it with other common database defaults, since these get mixed up often:
- MySQL/MariaDB: 3306
- Microsoft SQL Server: 1433
- MongoDB: 27017
- Redis: 6379

So if someone tells you "the database port," 5432 specifically means Postgres. An administrator *can* change this in `postgresql.conf`, so a given deployment isn't guaranteed to use 5432, but unless someone deliberately changed it, 5432 is what you'll find.

**Step 2: Is it safe to expose 5432 to the public internet?**

Short answer: **no, not as a general practice** — and I want to walk through why, including some positions I considered and rejected, because "just don't do it" isn't very actionable on its own.

*What "exposing" actually means technically:* binding the Postgres process to a public interface (or `0.0.0.0`) and configuring your firewall / cloud security group to allow inbound TCP 5432 from `0.0.0.0/0` (anywhere), rather than restricting it to a VPN, private subnet, or specific IPs.

*Reasons this is risky:*
1. **Automated scanning is constant and fast.** Tools like Shodan, masscan, and zmap continuously sweep the entire public IPv4 space for open database ports within minutes of a host coming online. An exposed 5432 will be found — this isn't a hypothetical, it happens almost immediately.
2. **Authentication depends on configuration you might get wrong.** Postgres's access control is layered through `pg_hba.conf` (host + database + user + auth method). Misconfigurations — like a `trust` line, or weak/reused passwords, or password auth without SSL — turn "found the port" into "logged in."
3. **Real-world precedent exists.** There have been documented mass-exploitation waves (e.g., the "Meow" attack and various ransom campaigns around 2020–2021) that specifically targeted internet-exposed Postgres and MongoDB instances, wiping data or leaving ransom notes in tables. This isn't theoretical risk; it's an attack pattern that has actually played out at scale.
4. **Unencrypted-by-default transport.** A stock install doesn't force SSL/TLS, so credentials and query data can be intercepted in transit unless you explicitly configure and enforce it (`sslmode=verify-full` on the client, `hostssl` entries in `pg_hba.conf`).
5. **Brute-force and credential-stuffing exposure.** Any exposed authentication endpoint invites automated login attempts, especially if there's no rate-limiting or account lockout (Postgres doesn't have built-in lockout after failed attempts).
6. **Unpatched CVEs.** Postgres has had network-exploitable vulnerabilities over the years; an exposed instance is only as safe as your patching discipline, and exposure raises the stakes of any lag there.
7. **Compliance implications.** Standards like PCI-DSS, HIPAA, and SOC 2 generally treat direct public exposure of a database as a finding/violation, since it collapses your defense-in-depth down to "the database's own auth" as the only remaining control.

*Alternatives I considered — and why I rejected them as sufficient on their own:*
- **"Just move it to a non-standard port."** This offers minor noise reduction against unsophisticated bots, but modern scanners check all 65,535 ports quickly, so it is not a real security control — only obscurity, not defense.
- **"A strong password is enough."** Rejected as a standalone solution: it doesn't protect against protocol-level vulnerabilities, misconfigured `pg_hba.conf` rules elsewhere, credential leakage from other systems, or unencrypted transport. Passwords are one layer, not the whole strategy.
- **"The cloud provider's firewall defaults to deny, so it's fine."** True as a starting posture, but irrelevant once you've deliberately opened the rule to `0.0.0.0/0` — which is exactly the scenario in question.
- **"It's a managed service (RDS, Cloud SQL, etc.), so it's handled for me."** Rejected as a blanket assumption: managed providers explicitly warn against enabling public accessibility and default to private-network-only access for good reason; the managed infrastructure secures the host OS and patching, not your decision to expose the endpoint.

*What I'd actually recommend instead:*
- Keep Postgres bound to a private network/VPC and reachable only from your application servers.
- For human/remote access, use an SSH tunnel, a bastion/jump host, or a VPN rather than opening the DB port directly.
- If some form of direct external access is unavoidable, layer controls: IP allowlisting in the firewall and `pg_hba.conf`, enforce SSL/TLS (`verify-full`), use SCRAM-SHA-256 auth with strong unique credentials or client certificates, disable remote superuser login, keep the server patched, and monitor/alert on connection logs (fail2ban-style rate limiting helps too).
- Consider a connection-pooling proxy (e.g., PgBouncer) or a cloud provider's private-endpoint/PrivateLink feature as an additional boundary between the internet and the database itself.

**Summary:** PostgreSQL's default port is 5432. Exposing it directly to the public internet is generally unsafe and is a well-documented attack vector (automated scanning finds it almost immediately, and there's real-world precedent of mass exploitation of exposed instances). Security-through-obscurity tricks like changing the port, or relying on a password alone, are not sufficient by themselves. The safer path is to keep Postgres on a private network and reach it via VPN/SSH tunnel/bastion host, reserving direct exposure (with heavy layered mitigations) for cases where there's truly no alternative.
