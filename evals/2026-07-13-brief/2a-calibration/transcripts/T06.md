You want the complete mental model of a TLS handshake: not the three-bullet "hello, exchange keys, encrypt" summary you'd get from a blog post, but the actual sequence of messages exchanged, what cryptography is happening underneath each step, why the protocol is shaped the way it is, how TLS 1.2 and TLS 1.3 differ, and the surrounding machinery (certificates, session resumption, extensions) that makes the whole thing work in practice. # 0. What problem the handshake is solving

Before any handshake message is sent, a plain TCP connection already exists (TLS assumes a reliable byte stream underneath — three-way TCP handshake, SYN/SYN-ACK/ACK, has already happened). TCP gives you *reliable, ordered delivery*, but zero confidentiality, zero integrity guarantees, and zero identity assurance — anyone on the path can read or alter every byte.

The TLS handshake exists to bootstrap, on top of that insecure channel, three properties without ever having met the other party before:

1. **Confidentiality** — a symmetric key that only the two endpoints know, so an eavesdropper sees ciphertext.
2. **Integrity/authenticity of the ongoing conversation** — assurance that no on-path attacker tampered with or reordered the negotiation or the data.
3. **Authentication** — proof (usually of the server, optionally of the client too) that you're talking to who you think you are, anchored in a certificate chain rooted at a trusted authority.

It has to do all this while an active attacker may be reading and modifying every packet in both directions in real time. That constraint is why the protocol looks the way it does — every design choice below traces back to defending against a specific class of active attacker.

# 1. The TLS 1.2 handshake, message by message

This is the "classical" flow (RFC 5246, 2008) and it's worth learning fully because a lot of intuition — and a lot of production traffic — still maps onto it.

**Flight 1 — Client → Server: `ClientHello`**
The client sends, in the clear:
- Highest TLS version it supports
- A 32-byte random value (`client_random`) — this will get baked into every key derived later, so replaying an old handshake can't reuse old keys
- A session ID (empty on a fresh connection, or a previous one if it wants to resume)
- An ordered list of cipher suites it's willing to use (e.g. `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`)
- Extensions: notably **SNI** (Server Name Indication — which hostname it's trying to reach, since one IP can host many TLS certificates), the elliptic-curve groups it supports, signature algorithms it accepts, and ALPN (which application protocol it'd like — HTTP/1.1 vs HTTP/2).

**Flight 2 — Server → Client**, several messages back-to-back:
- `ServerHello`: the server's random value, the cipher suite it picked from the client's list, chosen extensions (e.g. the ALPN result).
- `Certificate`: the server's X.509 certificate chain (its own leaf cert plus intermediate CA certs).
- `ServerKeyExchange` (only for DHE/ECDHE suites): the server generates a fresh, one-time-use Diffie-Hellman key pair and sends its public value, *signed* with the private key that corresponds to its certificate — this signature is what ties the ephemeral key exchange to the server's long-term identity.
- `CertificateRequest` (optional — only for mutual TLS, asking the client to also present a certificate).
- `ServerHelloDone`: "that's everything from me for now."

**Flight 3 — Client → Server:**
- `Certificate` (only if requested).
- `ClientKeyExchange`: depends on the cipher suite —
  - *Ephemeral Diffie-Hellman (DHE/ECDHE)*: client sends its own ephemeral public value; both sides now independently compute the same shared secret via Diffie-Hellman math, without it ever crossing the wire.
  - *Static RSA key exchange (legacy)*: client just generates a random "pre-master secret" itself and encrypts it directly with the server's RSA public key from the certificate.
- `CertificateVerify` (only if client cert was sent): client signs a hash of the handshake so far, proving it actually holds the private key for the certificate it presented, not just a copy of the public cert.
- Both sides now compute the **master secret** from the pre-master secret plus both randoms, via a PRF (in 1.2, HMAC-based, using the hash function named in the cipher suite, e.g. SHA-256). From the master secret they derive separate symmetric encryption keys, MAC keys, and IVs for each direction (client→server and server→client each get their own keys).
- `ChangeCipherSpec`: a one-byte message, technically its own tiny sub-protocol, meaning "everything after this from me is encrypted."
- `Finished`: the *first encrypted message*. It contains a MAC over a hash of literally every handshake message exchanged so far. This is what catches any tampering with the negotiation — if a man-in-the-middle altered which cipher suites were offered or removed an extension, the two sides' hashes of "what was actually said" diverge, and `Finished` fails to verify.

**Flight 4 — Server → Client:** `ChangeCipherSpec` and `Finished`, same idea, for the server's direction.

Only after both `Finished` messages verify does ordinary encrypted application data start flowing. Counting round trips: `ClientHello` → `ServerHello…ServerHelloDone` → `ClientKeyExchange…Finished` → `ChangeCipherSpec, Finished` — that's **two full round trips** before the client can be sure the channel is both encrypted *and* untampered-with (a client can technically start sending encrypted app data right after sending its own `Finished`, before hearing back — the risky variant of this optimization was literally called "False Start").

# 2. What TLS 1.3 changed, and why

TLS 1.3 (RFC 8446, 2018) is a substantial redesign, driven by two goals: fewer round trips, and encrypting as much of the handshake as early as possible.

**Flight 1 — Client → Server: `ClientHello`**
Same idea as before, but crucially it now includes a **`key_share`** extension: the client doesn't wait to be told which group to use — it *guesses* (usually correctly, since X25519 is the near-universal default today) and sends its ephemeral (EC)DHE public value immediately, for one or more groups.

**Flight 2 — Server → Client:**
- `ServerHello`, including its own `key_share`. **At this exact point, both sides can already compute the shared (EC)DHE secret** and derive a set of "handshake traffic keys." Everything the server sends after this is encrypted with those keys — including the certificate, unlike 1.2 where the certificate went across in plaintext.
- (encrypted) `EncryptedExtensions`, `CertificateRequest` (optional), `Certificate`, `CertificateVerify` (server signs the transcript hash), `Finished`.

If the server doesn't like any group the client guessed, it sends a `HelloRetryRequest` instead, asking the client to try again with a different group — this costs one extra round trip, but is rare in practice because clients guess well.

**Flight 3 — Client → Server:** (Client's own `Certificate`/`CertificateVerify` if requested) and `Finished`. The client can start sending application data right here — no need to wait for anything further.

That's **one round trip** to a fully encrypted, mutually verified channel — half of TLS 1.2's cost. The server, having derived keys as soon as it processed the client's `key_share`, can even push application data in the same flight as its own `Finished`, before it's heard anything back from the client.

**0-RTT (early data).** If the client and server have talked before (via a resumption ticket, see below), the client can send actual application data in its *very first* flight, with zero round trips of waiting. The catch: this data is encrypted using keys derived purely from a previously-shared secret, with no fresh randomness from the server involved yet — which means an attacker who captures that first flight can **replay** it and get the server to process the same request again. TLS 1.3 explicitly restricts 0-RTT to operations that are safe to replay (idempotent operations, or the application layer has to add its own anti-replay protection). This is a real, acknowledged trade-off in the spec, not an oversight — the working group considered it and shipped it with a big warning label rather than leaving the latency on the table entirely.

Also worth knowing: TLS 1.3 keeps a no-op `ChangeCipherSpec`-shaped message purely so that middleboxes (corporate proxies, old load balancers) that only know how to parse TLS 1.2 framing don't choke on it — that's a compatibility fossil, not a functional part of 1.3.

**Downgrade protection.** Because an active attacker could try to make a 1.3-capable client and server *think* the other side only supports 1.2 (or worse, 1.0), TLS 1.3 has the server embed a special fixed pattern inside part of its "random" value whenever it ends up negotiating a lower version than it's actually capable of. A 1.3-aware client checks for that pattern and aborts if it's present, since it means someone tampered with the negotiation.

| | TLS 1.2 (full handshake) | TLS 1.3 (full handshake) | TLS 1.3 (resumed / 0-RTT) |
|---|---|---|---|
| Round trips before app data | 2 | 1 | 0 |
| Certificate sent in cleartext? | Yes | No (encrypted once handshake keys exist) | N/A (no cert exchange on resume) |
| Static RSA key exchange allowed? | Yes (legacy) | No — removed entirely | — |
| Replay risk | None | None | Yes, for the early-data payload only |

# 3. The cryptographic machinery underneath

A few pieces get referenced above without full explanation — here's what's actually happening in each.

**(EC)DHE and why it gives forward secrecy.** Diffie-Hellman lets two parties who've never met derive a shared secret over a channel an eavesdropper can fully observe. Classically: agree on a prime `p` and generator `g`; each side picks a secret exponent (`a` for the client, `b` for the server), sends `g^a mod p` and `g^b mod p` in the clear; each side raises what it received to its own secret exponent, landing on the same value `g^(ab) mod p` — but computing that from just the two public values requires solving the discrete logarithm problem, which is computationally infeasible at the key sizes used. Elliptic-curve Diffie-Hellman (ECDHE, the dominant choice today — typically the curve X25519) is the same idea with point multiplication on an elliptic curve instead of modular exponentiation; smaller keys, same security margin.

The "E" for ephemeral is the important part: the server generates a *fresh* DH key pair for this connection alone and throws it away afterward — it only uses its long-term certificate private key to *sign* that ephemeral public value, never to encrypt anything directly. That separation is what gives you **forward secrecy**: if the server's long-term private key leaks a year from now, an attacker who recorded today's traffic still can't decrypt it, because today's actual encryption key depended on an ephemeral value that no longer exists anywhere. This is precisely why static RSA key exchange (where the client just encrypts the secret straight to the server's long-term RSA public key) doesn't have this property — a single future key compromise retroactively breaks every session ever recorded. That gap is a major reason TLS 1.3 removed static RSA/DH key exchange entirely and only permits ephemeral exchange (or PSK-based resumption, discussed below).

**Certificate validation.** The server's certificate is checked against a **chain of trust**: leaf certificate → one or more intermediate CA certificates → a root CA certificate that's already pre-installed as trusted in the OS or browser's trust store. At each link, the client verifies the issuing certificate's signature over the next one down, checks validity dates, checks that the hostname you're connecting to matches one of the certificate's Subject Alternative Names, and checks basic/extended key usage constraints (e.g., that a CA cert is actually marked allowed to sign other certs). Revocation is the messier part in practice: the formal mechanisms are CRLs (certificate revocation lists) and OCSP (a live "is this cert still good?" query, often "stapled" onto the handshake by the server so the client doesn't have to make a separate request), but real deployments lean heavily on browser-vendor-curated aggregated revocation lists (e.g., Chrome's CRLSet) because live revocation checking is slow and often fails open. Modern publicly-trusted certificates are also expected to appear in **Certificate Transparency** logs — public, append-only logs of issued certificates — which is a check against a CA mis-issuing a cert for a domain without the domain owner noticing.

**The record layer after the handshake.** Once keys are derived, actual application data travels in TLS records protected by an AEAD cipher (AES-GCM or ChaCha20-Poly1305 are the common ones) — a single cryptographic operation that gives you both confidentiality and a tamper-evident tag in one pass, which is why older constructions (separate MAC-then-encrypt with CBC-mode block ciphers) have been phased out. Each record carries an implicit sequence number so an attacker can't replay or reorder records within the connection.

**Key derivation is layered, not a single shared key.** In TLS 1.3, the DH shared secret doesn't get used directly — it feeds an HKDF-based "key schedule" that ratchets through an early secret, a handshake secret, and a master secret, at each stage deriving *separate* traffic secrets for the handshake phase versus the application-data phase, and separate secrets per direction. So over the life of one connection there isn't "a key" — there are several, each scoped to a phase and a direction, which limits the blast radius if any one derived value were somehow exposed. TLS 1.2 also separates client-write and server-write keys, though it doesn't separate handshake-phase keys from application-phase keys the way 1.3 does, since in 1.2 the handshake itself was mostly unencrypted anyway.

# 4. Session resumption (avoiding the full handshake on repeat visits)

Doing a full asymmetric handshake every time is wasteful, so both versions support resuming a previous session cheaply:

- **TLS 1.2**: either the client echoes a previous session ID and the server keeps enough server-side state to recall the old master secret (an abbreviated handshake, skipping certificate exchange and key exchange), or the server hands the client an encrypted "session ticket" it can present later, letting the server stay stateless.
- **TLS 1.3**: after a full handshake completes, the server sends a `NewSessionTicket` message containing a PSK (pre-shared key) identity. Next connection, the client presents that ticket, both sides derive fresh keys from the PSK plus a *new* (EC)DHE exchange for continued forward secrecy, and — if the client is willing to accept the replay risk described earlier — it can attach 0-RTT application data to that very first flight.

# 5. Design alternatives TLS's own history considered and rejected

This is worth walking through explicitly, because it explains *why* the protocol looks the way it does rather than some other reasonable-sounding way it could have been built:

- **Static RSA key exchange** (client encrypts the secret to the server's long-term public key) was the original default. Rejected/deprecated because of the forward-secrecy gap above, and TLS 1.3 removed it outright, permitting only ephemeral (EC)DHE or PSK resumption.
- **Compression at the TLS layer** used to be optional. Rejected after the CRIME attack showed that compression ratios leak information about secret content (like cookies) mixed into the compressed stream — compression was dropped from the protocol.
- **CBC-mode block ciphers** (paired with a separate MAC) were the workhorse symmetric construction for years. Rejected in practice after a string of attacks against exactly this construction — predictable IVs (BEAST), padding-oracle timing leaks (Lucky13), and the SSL 3.0 fallback variant (POODLE) — pushed the ecosystem toward AEAD ciphers (AES-GCM, ChaCha20-Poly1305), which TLS 1.3 makes mandatory by only defining AEAD-based cipher suites.
- **RC4** was offered for years as a way to sidestep CBC issues entirely. Rejected once statistical biases in its keystream were shown to be practically exploitable; it's now banned outright in modern TLS.
- **Deliberately weakened "export-grade" cipher suites** (a leftover of 1990s US cryptography export restrictions, offering 512-bit RSA/DHE) stuck around in server configurations far longer than intended. Their continued presence, combined with implementation bugs, enabled the FREAK and Logjam attacks, where an active attacker could coerce a connection down to the weak suite and break it in real time or via precomputation. Rejected going forward: export suites are gone, and both explicit downgrade-detection (the `TLS_FALLBACK_SCSV` mechanism, and TLS 1.3's downgrade sentinel described above) and removal of the weak suites closed this off.
- **In-session renegotiation** (renegotiating parameters mid-connection) had a real vulnerability (an attacker could inject data before a renegotiation in a way the application would attribute to the wrong identity — CVE-2009-3555). TLS 1.3 rejected the whole mechanism and replaced the narrow legitimate use case (rotating keys on a long-lived connection) with a simpler, safer `KeyUpdate` message.
- **2-RTT full handshake** was accepted as the cost of doing business through TLS 1.2's life, but the TLS 1.3 working group treated round-trip latency as a first-class design constraint (partly under pressure from the web-performance/QUIC community) and restructured the message flow specifically to cut it to one round trip, accepting real complexity (the `HelloRetryRequest` fallback path, the 0-RTT replay caveat) in exchange.

# 6. Adjacent pieces worth knowing, for a genuinely complete picture

- **SNI** is what lets one IP address serve TLS for many different hostnames — the client says which hostname it wants before the server picks a certificate. It's sent in the clear in both 1.2 and 1.3 today, which leaks which site you're visiting to anyone on the path; **Encrypted Client Hello (ECH)** is a newer extension, increasingly deployed by large providers, that encrypts this too.
- **ALPN** is the extension that lets the same handshake also settle whether the connection will speak HTTP/1.1 or HTTP/2 afterward.
- **Mutual TLS (mTLS)** is the same handshake with the optional client-certificate branch exercised — common in service-to-service auth, not typical browser-to-website traffic.
- **QUIC/HTTP3** doesn't run TLS "on top of" a transport handshake the way HTTPS-over-TCP does — it embeds the TLS 1.3 handshake directly into its own transport handshake (RFC 9001), so the cryptographic and transport setup happen together rather than TLS waiting for TCP to finish first.
- **Post-quantum readiness**: hybrid key exchange (classical X25519 combined with a post-quantum KEM, standardized by NIST as ML-KEM) is increasingly being deployed by default by major browsers and CDNs, specifically to protect today's traffic against "harvest now, decrypt later" attacks by a future quantum computer — this plugs into the handshake at exactly the `key_share` step, without otherwise changing the protocol's shape.
- **DTLS** applies the same ideas over UDP (for things like WebRTC and some VPNs), with extra bookkeeping to handle unreliable, unordered delivery that TCP would normally have solved for free.

# Summary

A TLS handshake is the process by which two parties who've never spoken before, over a channel an active attacker can read and modify, agree on a protocol version and cipher suite, authenticate the server (and optionally the client) via a certificate chain rooted in a pre-installed trust anchor, and derive a set of symmetric keys — without ever transmitting those keys in a form an eavesdropper could extract — while detecting any tampering with the negotiation itself. TLS 1.2 does this in two round trips via `ClientHello`/`ServerHello`/certificate exchange/`ClientKeyExchange`/`Finished`, with the certificate and most negotiation sent in the clear. TLS 1.3 restructures this into one round trip by having the client guess and send its key-share immediately, letting both sides derive handshake keys right after `ServerHello` and encrypt everything from that point on, and it removes several legacy mechanisms (static RSA key exchange, compression, renegotiation, weak cipher suites) that history showed to be actively harmful. Underneath, ephemeral Diffie-Hellman is what buys forward secrecy, certificate-chain validation (plus increasingly, Certificate Transparency) is what buys authentication, and an AEAD-protected record layer with per-direction, per-phase derived keys is what protects the actual application data. Session resumption (tickets/PSK) and 0-RTT trade a small, explicitly-acknowledged replay risk for skipping the handshake entirely on repeat connections.
