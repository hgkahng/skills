TLS's handshake has one job: let client and server agree on symmetric encryption keys and authenticate the server, before any application data is sent, without a passive or active attacker learning the keys or impersonating the server.

Modern flow (TLS 1.3, 1 round trip):

1. **ClientHello** — client sends: supported TLS versions, cipher suites, a random nonce, supported elliptic-curve groups, and (the 1.3 shortcut) a `key_share` — an ephemeral public key for one or more guessed groups. Also SNI (which hostname it wants, so the server picks the right cert) and ALPN (e.g. "h2" for HTTP/2).
2. **ServerHello** — server picks a cipher suite and group, replies with its own random and its own ephemeral `key_share`. Both sides now run ECDHE and get the same shared secret — this is the point where key agreement is done, after just one round trip.
3. **Key derivation** — both feed the shared secret through HKDF to get handshake traffic keys. Everything from here in the same flight is encrypted.
4. **Server** sends EncryptedExtensions, its certificate chain, a **CertificateVerify** (a signature over the whole handshake transcript so far, made with the certificate's private key — proves the server actually holds that key), and a **Finished** message (a MAC over the transcript, proving both sides saw the same handshake, blocking downgrade/tampering).
5. **Client** validates the cert chain (trust anchor, expiry, revocation, and that the hostname matches the cert's SAN), checks the CertificateVerify signature, checks the server's Finished, then sends its own Finished (and, only for mutual TLS, its own certificate + CertificateVerify).
6. Both sides derive a **separate** set of application traffic keys from the handshake secret (key separation, so compromising one doesn't expose the other). Application data now flows under an AEAD cipher (AES-GCM or ChaCha20-Poly1305), with per-record nonces from a sequence number.

Caveats that matter: TLS 1.2 needed 2 round trips, used explicit ChangeCipherSpec messages, and allowed static-RSA key exchange with no forward secrecy (a leaked server key retroactively decrypts old traffic) — TLS 1.3 dropped RSA key exchange and non-forward-secret ciphers entirely. TLS 1.3 also supports 0-RTT session resumption for lower latency, but early data sent in that mode is replayable and should never carry non-idempotent requests.
