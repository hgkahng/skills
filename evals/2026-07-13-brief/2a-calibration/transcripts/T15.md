# TLS Handshake Explained

The TLS (Transport Layer Security) handshake is how a client and server establish a secure channel: they agree on cryptographic parameters, authenticate the server (and optionally the client), and derive shared secret keys — all before any application data (like an HTTP request) is exchanged. I'll walk through TLS 1.3 (the current standard, RFC 8446) since it's the cleanest version, then cover how TLS 1.2 differs, since a lot of deployed traffic still uses it.

## Before TLS begins: TCP

TLS runs on top of a reliable transport, almost always TCP. A standard TCP three-way handshake (SYN, SYN-ACK, ACK) happens first. Only after that completes does the TLS handshake start, as the first data sent over that connection.

## The three problems the handshake solves

1. **Negotiation** — agree on a protocol version, cipher suite, and extensions both sides support.
2. **Authentication** — prove the server is who it claims to be via its X.509 certificate (and optionally the client too, in mutual TLS).
3. **Key establishment** — derive a shared secret that only the two endpoints know, without ever sending that secret itself over the wire, then use it to derive several distinct symmetric keys.

## Step-by-step (TLS 1.3, the common 1-RTT case)

**1. ClientHello (client → server)** — sent in the clear:
- Supported TLS version(s)
- A list of supported cipher suites (e.g., `TLS_AES_128_GCM_SHA256`, `TLS_CHACHA20_POLY1305_SHA256`)
- A random 32-byte nonce ("client random")
- Supported key-exchange groups (elliptic curves like X25519, secp256r1)
- A **key_share** extension — the client optimistically sends its own ephemeral Diffie-Hellman public value for one or more groups, guessing what the server will want. This guess is what collapses the handshake to one round trip.
- Server Name Indication (SNI) — the hostname it's trying to reach, so a server hosting many domains on one IP picks the right certificate
- ALPN — to negotiate the application protocol (e.g., HTTP/2 vs HTTP/1.1)
- Signature algorithms it can verify, session tickets for resumption, etc.

**2. ServerHello (server → client)** — the server picks one cipher suite and one key-exchange group from the offers, and replies with its chosen version/suite, its own random nonce ("server random"), and its own ephemeral key-share public value.

At this point — after just these two messages — **both sides can independently compute the same shared secret** via (Elliptic-Curve) Diffie-Hellman, without it ever crossing the wire. Everything the server sends from here on is encrypted with keys derived from that secret (a major change from TLS 1.2, where most of this was plaintext).

**3. Server's remaining flight (encrypted)**:
- **EncryptedExtensions** — extension data that doesn't need to be public
- **CertificateRequest** (optional) — if the server wants a client certificate too
- **Certificate** — the server's X.509 chain (leaf cert plus intermediates)
- **CertificateVerify** — a signature over a hash of the entire handshake transcript so far, made with the private key matching the certificate's public key. This is what actually *proves* possession of the private key — the certificate alone is just a public key plus identity claims.
- **Finished** — an HMAC over the whole transcript, keyed from the derived handshake secret, proving the server derived the correct keys and that nothing was tampered with.

**4. Client verifies and responds**. The client validates the certificate chain up to a trusted root CA already in its trust store (checking signatures link by link, validity dates, and that the hostname matches a Subject Alternative Name on the cert — often also checking revocation via OCSP, frequently via "OCSP stapling" so the server proactively attaches a signed freshness proof). It verifies the CertificateVerify signature and the server's Finished MAC, then sends its own **Finished** (plus its own Certificate/CertificateVerify if client auth was requested).

**5. Application data.** Both sides derive separate "application traffic secrets" and start exchanging real data (e.g., HTTP) encrypted with a symmetric AEAD cipher like AES-GCM or ChaCha20-Poly1305, wrapped in TLS records.

```
Client                                           Server
ClientHello
+ key_share, SNI, ALPN, etc.  -------------->
                                              ServerHello
                                              + key_share
                                              {EncryptedExtensions}
                                              {CertificateRequest*}
                                              {Certificate}
                                              {CertificateVerify}
                              <--------------  {Finished}
{Certificate*}
{CertificateVerify*}
{Finished}                    -------------->
[Application Data]           <------------->  [Application Data]
```
(`{}` = encrypted with handshake keys, `[]` = encrypted with application keys, `*` = only with client auth)

## What's happening cryptographically underneath

- **Key exchange**: modern TLS uses ephemeral Diffie-Hellman, almost always elliptic-curve (ECDHE, e.g., X25519). "Ephemeral" means a fresh key pair is generated per-connection and discarded afterward — this is what gives **forward secrecy**: even if the server's long-term certificate key is later stolen, past sessions recorded off the wire still can't be decrypted, because the shared secret for each session depended on keys that no longer exist anywhere.
- **Key schedule**: the raw DH output isn't used directly. TLS 1.3 runs it through HKDF along with hashes of the transcript at various points, producing a tree of distinct keys — early secret (for 0-RTT), handshake traffic secrets (used only to encrypt the handshake messages themselves), and application traffic secrets (for actual data). Separating these means compromising one doesn't hand over the others, and cryptographically binds every derived key to this exact handshake's transcript.
- **Finished messages**: an HMAC over a hash of everything exchanged so far, computable only if you hold the shared secret. This detects tampering or a mismatched view of the negotiation (e.g., a downgrade attempt) — alter any earlier message and the transcript hash won't match, so the Finished check fails.
- **Certificate chain trust**: the leaf cert is signed by an intermediate CA, itself signed by a root CA shipped in the OS/browser trust store. Validation means checking each signature, each cert's validity window, key usage/basic constraints, and that the leaf's identity matches the hostname requested via SNI.

## Session resumption and 0-RTT

To avoid paying full handshake cost every time, TLS 1.3 supports resumption via a **PSK (pre-shared key)**: after a first handshake, the server hands the client an opaque session ticket. On a later connection, the client presents it, and both sides derive new keys from the earlier shared secret plus fresh randoms — skipping certificate verification and key exchange (or combining the PSK with a fresh ECDHE exchange to keep forward secrecy on the resumed session too).

TLS 1.3 also allows **0-RTT**: the client can send encrypted application data in its very first flight, before hearing back from the server, using keys derived from the earlier session's PSK. This is fast but has a real caveat: 0-RTT data has no protection against replay — an attacker who captures that first flight can resend it, and the server may process it again. Because of this, 0-RTT is normally restricted to idempotent requests, with the application opting in deliberately.

## How TLS 1.2 differs

- **Two round trips instead of one** — key exchange happens via separate ClientKeyExchange/ServerKeyExchange messages rather than key shares riding along with the Hellos, so the full handshake is typically 2-RTT.
- **Much less of the handshake is encrypted** — certificates and key-exchange parameters go out in plaintext, leaking metadata (a core motivation for the 1.3 redesign).
- **An explicit "ChangeCipherSpec" message** announces "everything after this is encrypted." TLS 1.3 dropped this as unnecessary (keeping a dummy version only for middlebox compatibility).
- **Static RSA key exchange was allowed** — the client could just encrypt a "pre-master secret" with the server's RSA public key straight from the certificate, no Diffie-Hellman involved. That provides **no forward secrecy**: if the server's private key is ever compromised, every past session recorded off the wire can be decrypted retroactively. TLS 1.3 removed this option entirely and mandates ephemeral (EC)DHE.
- **Renegotiation** — TLS 1.2 allowed renegotiating parameters mid-connection, which had real vulnerabilities (e.g., the 2009 renegotiation attack); 1.3 designed this away.
- Weaker legacy ciphers were still permitted under 1.2 (CBC-mode suites vulnerable to padding-oracle attacks like BEAST/Lucky13, MD5/SHA-1-based suites); TLS 1.3 restricts cipher suites to a short, modern, AEAD-only list.

## After the handshake: the record layer

Once keys are established, all traffic — handshake or application — travels as TLS **records**: a small header (content type, version, length) followed by an AEAD-encrypted payload (ciphertext plus authentication tag). AEAD gives confidentiality and integrity together, so each record is both encrypted and tamper-evident — flip a bit in transit and decryption fails outright rather than delivering corrupted data silently.

## The short version

1. Client and server agree on a protocol version and cipher suite.
2. They run an ephemeral Diffie-Hellman exchange to derive a shared secret that never crosses the wire.
3. HKDF turns that secret into separate handshake and application keys.
4. The server (and optionally the client) proves its identity via a certificate plus a signature over the handshake transcript.
5. Both sides send a Finished MAC confirming matching keys and an untampered transcript.
6. All following data is protected with fast symmetric AEAD encryption using the derived application keys.

That split — asymmetric crypto to authenticate and bootstrap a secret, symmetric crypto for the actual bulk data — is what lets TLS be both secure and fast enough to be invisible on every HTTPS page load.
