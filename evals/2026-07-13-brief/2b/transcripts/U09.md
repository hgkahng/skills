Here are the most common culprits, roughly in order of how often they're the actual problem:

**1. Poor layer caching / instruction ordering**
This is the #1 cause. If you `COPY . .` before installing dependencies, every code change invalidates the cache and forces a full dependency reinstall. Fix: copy only dependency manifests (`package.json`, `requirements.txt`, `Cargo.toml`, etc.), install dependencies, *then* copy the rest of the source.

**2. Large build context**
Docker sends the entire build context to the daemon before building anything. If you don't have a `.dockerignore`, things like `.git`, `node_modules`, build artifacts, or logs get sent every time. This can add seconds to minutes before the build even starts.

**3. No multi-stage builds**
Without them, build tools, compilers, and intermediate artifacts stay in the final image, bloating layers that need to be written/cached/pushed. Multi-stage builds also let you cache a "dependencies" stage separately from your "build" stage.

**4. Not using BuildKit / cache mounts**
Legacy builder doesn't parallelize independent stages and lacks `--mount=type=cache`. Without cache mounts, package managers (npm, pip, apt, cargo, go mod) redownload everything on every build instead of reusing a persistent cache. Enabling BuildKit (`DOCKER_BUILDKIT=1`, default in recent Docker) plus `RUN --mount=type=cache,target=...` is often the single biggest speedup for dependency-heavy builds.

**5. Heavy or wrong base images**
Full OS images (`ubuntu`, `debian`) vs. `-slim`/`alpine`/`distroless` variants pull more data and often trigger more package installs. Also check if you're pulling from a slow/distant registry mirror.

**6. Redundant/unmerged RUN layers**
Each `RUN` is a layer; separate `apt-get update`, `apt-get install`, and cleanup steps (instead of one chained command) create bloated, harder-to-cache layers and more filesystem overhead.

**7. No CI/remote build cache**
In CI, every run may start from zero if you're not using `--cache-from`, registry cache, or a persistent runner/cache volume — so even a well-ordered Dockerfile rebuilds everything from scratch each time.

**8. Emulated multi-platform builds**
Building `linux/arm64` on an `amd64` host (or vice versa) via QEMU is dramatically slower than native builds — this alone can 5-10x your build time.

**9. Docker Desktop overhead (Mac/Windows)**
Bind-mounted volumes and the VM/filesystem translation layer (virtiofs, gRPC FUSE) add real overhead, especially for I/O-heavy steps like `npm install` on a mounted volume.

**10. Resource limits**
Docker Desktop or CI runners with low CPU/memory allocations bottleneck parallel layer builds and package compilation.

Quick things to check first: are you on BuildKit, do you have a `.dockerignore`, and is your Dockerfile ordered so that `COPY package*.json` / dependency install happens before `COPY . .`? Those three fixes resolve the majority of "slow Docker build" complaints. If you share your Dockerfile, I can point to the specific lines causing cache misses.
