Both integrate changes from one branch into another, but they do it differently:

**`git merge`**
- Combines the histories of two branches by creating a new "merge commit" that has two parents.
- Preserves the exact history of what happened — you can see when branches diverged and were joined.
- Non-destructive: it never changes existing commits.
- Downside: on long-lived branches, history can get cluttered with lots of merge commits.

```
      A---B---C feature
     /         \
D---E---F---G---H  main (H is the merge commit)
```

**`git rebase`**
- Takes the commits from your branch and replays them one by one on top of another branch's tip, creating new commits with new hashes.
- Produces a clean, linear history — looks as if you'd built your feature starting from the latest main.
- Rewrites history: the original commits are replaced, which is why you should avoid rebasing commits that others have already pulled/based work on.

```
D---E---F---G---A'---B'---C'  (feature rebased onto main)
```

**Rule of thumb:**
- Use `rebase` to clean up your own local/feature branch before sharing it (e.g., `git rebase main` to catch up with the latest changes, or interactive rebase to tidy commits).
- Use `merge` when combining work that others rely on or already have (e.g., merging a feature branch into `main`), since it doesn't rewrite shared history.
- Avoid rebasing commits that have already been pushed and shared, unless you're prepared to force-push and everyone involved knows to handle that (`git push --force-with-lease`).

Many teams follow "rebase locally, merge (or use a squash-merge) for the final integration into a shared branch" as a good middle ground.
