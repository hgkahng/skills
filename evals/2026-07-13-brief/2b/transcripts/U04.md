# Hunting a Memory Leak in Node.js — Full Walkthrough

## Step 0: Get the mental model right

Node memory leaks are almost never "malloc without free" — V8 has a real garbage collector. A "leak" in practice means: **something keeps a reference to an object that should be dead**, so GC can never collect it. Your job is not "find the leak," it's "find the retainer" — the piece of your code still holding a pointer to garbage.

Also distinguish a real leak from normal behavior first:
- **Sawtooth memory graph** (climbs, drops on GC, climbs, drops) = normal. Healthy.
- **Staircase/monotonic climb that never drops back to baseline even after a full GC** = leak.
- **High but flat memory** = maybe just a big working set (large cache, big buffers) — not a leak, might just need tuning.

Don't skip this distinction. People "fix" leaks that were just GC not having run yet.

## Step 1: Confirm it's real with cheap instrumentation

Before touching heap snapshots, add logging:

```js
setInterval(() => {
  const m = process.memoryUsage();
  console.log({
    rss: (m.rss / 1024 / 1024).toFixed(1) + 'MB',
    heapTotal: (m.heapTotal / 1024 / 1024).toFixed(1) + 'MB',
    heapUsed: (m.heapUsed / 1024 / 1024).toFixed(1) + 'MB',
    external: (m.external / 1024 / 1024).toFixed(1) + 'MB',
    arrayBuffers: (m.arrayBuffers / 1024 / 1024).toFixed(1) + 'MB',
  });
}, 10_000);
```

Key fields:
- `heapUsed` — your JS objects. Growth here = JS-level leak (arrays, maps, closures, listeners).
- `external` / `arrayBuffers` — Buffers, TypedArrays, native bindings. Growth here = leaked Buffers/streams or a native addon.
- `rss` — total process memory. Can grow even when `heapUsed` looks fine (fragmentation, native leaks) — worth knowing which one is actually rising.

Run it under **steady, repeated load** (not just idle) for 10–20+ minutes. Log every request count or every N seconds and graph it (even just pasting into a spreadsheet). You want to see the shape of the curve, not a single number.

Also start the process with GC tracing so you can see what happens across full collections, not just scavenges:

```bash
node --trace-gc server.js
```

Look specifically at **Scavenge** (minor GC, cheap, frequent) vs **Mark-sweep-compact** (major GC, expensive, less frequent). The number that matters is heap size *right after* a Mark-sweep-compact. If that number keeps increasing collection after collection under identical repeated load, you have a real leak — because that's V8 telling you "even after doing everything I can, this much is still reachable."

You can also force a full collection to strip out "hasn't been collected yet" noise:

```bash
node --expose-gc server.js
```
```js
global.gc();
console.log(process.memoryUsage().heapUsed);
```

## Step 2: Build a reliable repro

You need a tight loop that reproduces growth in minutes, not days. Use a load generator against the specific route(s) you suspect:

```bash
npx autocannon -c 50 -d 120 http://localhost:3000/your-route
```

If you don't know which route, hit them one at a time, or hit everything and narrow down later using heap diffs (next step). The point of a repro is that you can run it, snapshot, run it again, snapshot again, and see what grew *proportionally to the requests you sent* — that's your signal in a sea of noise.

---

## Step 3: Take heap snapshots (the core technique)

### 3a. Start Node with the inspector

```bash
node --inspect server.js
# remote/Docker: bind to all interfaces, and make sure the port is only reachable internally
node --inspect=0.0.0.0:9229 server.js
```

### 3b. Open Chrome DevTools against it

- Open Chrome, go to `chrome://inspect`.
- Under "Remote Target," click **inspect** next to your process (add `host:port` under "Configure" if it's remote/Docker-forwarded).
- Go to the **Memory** tab.

### 3c. The 3-snapshot technique (this is the important part — don't just take one)

1. Let the app sit idle a moment after startup, then **take Snapshot 1** (baseline).
2. Run your load generator for the repro (Step 2).
3. **Take Snapshot 2.**
4. Run the exact same load again.
5. **Take Snapshot 3.**

Why three: comparing 1→2 alone is noisy (startup caches, first-request JIT warmup, lazy-initialized singletons all show up as "growth" that isn't a leak). Objects that grow from **2→3 by roughly the same amount that grew 1→2, proportional to identical repeated load**, are your real suspects — one-time growth washes out, per-request growth repeats.

### 3d. Use the Comparison view

- Select Snapshot 3, switch the dropdown from "Summary" to **"Comparison"**, compare against Snapshot 2.
- Sort by **`# Delta`** (object count growth) and separately by **`Size Delta` / retained size**.
- Ignore native/internal categories at first (`(system)`, `(compiled code)`); focus on **your own constructor names** — the classes/objects your code created (e.g. `Object`, arrays, or better, named classes/closures from your codebase).
- Click into a growing entry → bottom panel shows **Retainers**. Expand the retainer chain upward (it reads bottom-up: "this object is held by X, which is held by Y..."). Keep expanding until you hit something recognizable from *your* code — a variable name, a module-level `const cache = {}`, an array you push to, an EventEmitter's `_events`.

That retainer chain is the answer. It literally tells you the line of code (or at least the structure) that's holding the reference.

## Step 4: If snapshot diffing is too noisy, use allocation sampling instead

Snapshots show *what's alive right now*; sometimes you want *what keeps getting allocated and not freed over time*. Use the sampling heap profiler:

```bash
node --heap-prof server.js
```

This writes a `.heapprofile` file on exit (or `node --heap-prof --heap-prof-interval=... server.js` to tune sampling). Load that file in DevTools Memory tab ("Load" button) — it shows an allocation flamegraph by call stack, so you can see exactly which function is the top allocator over the run, sorted by "Self Size" that never gets freed.

Alternatively, `clinic.js` wraps a lot of this nicely:

```bash
npm install -g clinic
clinic doctor -- node server.js       # run this first — tells you IF it's a memory issue vs event-loop/I/O issue
clinic heapprofiler -- node server.js # if doctor points at memory
```

Hit it with `autocannon` while clinic is running, then Ctrl+C — it generates an HTML report with flamegraphs pointing at the allocation sites.

## Step 5: Do this safely in production (no `--inspect` needed)

You often can't attach a live inspector to prod. Two options:

**a) Signal-triggered snapshot with the `heapdump` module:**
```bash
npm install heapdump
```
```js
require('heapdump'); // auto-registers SIGUSR2 handler
```
```bash
kill -USR2 <pid>   # writes a heapsnapshot file to cwd
```
Copy the `.heapsnapshot` file to your laptop, load it into Chrome DevTools Memory tab, diff as in Step 3.

**b) Native V8 API, no dependency, trigger however you like (HTTP admin route, signal, etc.):**
```js
const v8 = require('v8');
const fs = require('fs');

function dumpHeap(label) {
  const stream = v8.getHeapSnapshot();
  const out = fs.createWriteStream(`/tmp/${label}-${Date.now()}.heapsnapshot`);
  stream.pipe(out);
}
```

For longer-running visibility, ship `process.memoryUsage()` to your metrics system (Prometheus/Datadog/etc.) and graph `heapUsed`/`rss` per pod over days — container orchestrators (k8s OOMKill, ECS) restarting pods on a regular period is itself a strong leak signal, and the graph shape across restarts tells you the leak rate.

## Step 6: The usual suspects (check these first — they cover ~90% of real cases)

1. **Unbounded module-level cache/object/Map/array**, e.g.:
   ```js
   const cache = {};
   app.get('/user/:id', (req, res) => {
     cache[req.params.id] = req.body; // never evicted, grows forever
   });
   ```
   Fix: TTL/LRU cache (e.g. `lru-cache`) with a max size, not a plain object/Map.

2. **Event listeners added but never removed**, especially inside a request handler or a per-connection callback:
   ```js
   function onConnection(socket) {
     emitter.on('update', () => socket.send(...)); // new listener every connection, never removed
   }
   ```
   Node will actually warn you: `MaxListenersExceededWarning`. Treat that warning as a leak alarm, not noise — track it down, don't just raise the limit.

3. **Timers not cleared**: `setInterval`/`setTimeout` referencing closures that capture large request/response objects, never `clearInterval`'d when the thing they're tied to (a connection, a job) ends.

4. **Express `session` default `MemoryStore`** in production — it's explicitly documented as not production-safe, grows unbounded with sessions. Use Redis/DB-backed session store.

5. **Streams/sockets not properly closed** — leftover listeners and buffered chunks on a stream that was abandoned instead of `.destroy()`'d. Watch `external`/`arrayBuffers` in `memoryUsage()` for this category specifically.

6. **DB/connection pool misuse** — connections/clients checked out and never released back to the pool, so each one plus its buffers stays retained.

7. **Closures over large scope captured somewhere long-lived** — e.g. a logger or middleware that captures the entire `req` object in a closure stored in an array/queue for "later," and later never comes, or comes very slowly.

8. **`AsyncLocalStorage` / continuation-local storage** holding onto request-scoped context longer than the request, because something copied the store reference into a longer-lived structure.

9. Circular references are **not** a cause — V8's GC (mark-and-sweep) handles cycles fine. Don't waste time chasing these.

---

## Step 7: Prove the fix

Once you patch the retainer (bound the cache, remove the listener, clear the timer, close the stream):

1. Re-run the exact same 3-snapshot / load-test procedure.
2. Confirm `heapUsed` after a forced `global.gc()` returns to near-baseline after the load stops.
3. Run the load test 3-5x longer than before to make sure it's not just a slower leak.
4. Deploy and watch the production memory graph over at least one full day/traffic-cycle before declaring victory — some leaks are tied to specific traffic patterns (cron jobs, a rare endpoint, an edge-case payload) that a short local load test won't trigger.

## Cheat sheet

```bash
# quick signal
node --trace-gc server.js

# live inspection
node --inspect=0.0.0.0:9229 server.js   # then chrome://inspect → Memory tab

# allocation profiling
node --heap-prof server.js              # load .heapprofile into DevTools

# guided diagnosis
clinic doctor -- node server.js
clinic heapprofiler -- node server.js

# load generator to trigger it
npx autocannon -c 50 -d 120 http://localhost:3000/route

# production snapshot without --inspect
kill -USR2 <pid>     # with `require('heapdump')` loaded
```

Core technique to remember above all else: **3 snapshots, not 1** (baseline → load → load again), diff 2-vs-3 in Comparison view, sort by delta, walk the Retainers panel up to your own code.
