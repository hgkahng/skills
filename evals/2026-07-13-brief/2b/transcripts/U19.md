Yes, the GIL still exists in standard CPython and still blocks true parallel execution of Python bytecode across threads, but it rarely matters for a typical web app. Most web workloads are I/O-bound—database queries, HTTP calls, file reads—and the GIL releases during I/O, so threads or async/await still give real concurrency there. Production setups (Gunicorn, uWSGI) typically scale by running multiple processes/workers rather than relying on multi-threading for CPU parallelism, sidestepping the GIL entirely. Where it actually bites is CPU-bound work—heavy computation, image processing, ML inference—run via threads inside one process; there you won't get multi-core speedup without multiprocessing, C extensions that release the GIL (numpy, etc.), or offloading to a separate service/worker queue. Python 3.13 introduced an experimental free-threaded build (PEP 703) making the GIL optional, but it's not yet default and library/ecosystem support is still maturing. For a standard CRUD web app: don't worry about it. If you later add heavy in-process CPU work, revisit then.
