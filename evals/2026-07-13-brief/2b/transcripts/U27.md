# Hunting Down a Memory Leak in a Node.js Service — Full Walkthrough

This is a long process broken into phases: confirm, instrument, reproduce, capture, analyze, diagnose, fix, verify, prevent. Don't skip phases — jumping straight to "let me look at a heap snapshot" without confirming and reproducing first is the most common way people waste a day chasing a ghost.

---

## Phase 0: Confirm you actually have a leak

Not all memory growth is a leak. Node/V8 will happily let the heap grow toward its ceiling before doing a full GC, because full GCs are expensive and V8 avoids them when it can. So "memory keeps climbing in a dashboard" is not proof of a leak by itself.

**What a real leak looks like:** RSS or heapUsed climbs over hours/days under roughly steady traffic and *never comes back down*, even during quiet periods, even after forced garbage collection. Eventually the process OOMs or hits `--max-old-space-size` and crashes with `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`.

**What normal healthy memory looks like:** a sawtooth pattern — heap grows as requests come in, garbage collector runs, heap drops back down to roughly the same baseline, repeat. The *baseline* stays flat over time even though the instantaneous value oscillates.

So step one, before touching any profiler:

1. Graph `process.memoryUsage()` (or your APM's Node memory metrics) over a long window — at least several hours, ideally a day or two — under normal production-like traffic.
2. Look specifically at the **baseline after each GC dip**, not the peaks. Is the floor of the sawtooth rising over time, or flat?
3. Check whether restarts/OOM-kills correlate with time-since-deploy or time-since-restart. If every pod dies roughly N hours after starting regardless of load, that's a strong leak signal.
4. Check if the growth correlates with a specific trigger — a particular endpoint, a batch job, a cron task, a specific customer's traffic pattern — versus generic uptime. This will save you enormous time later because it tells you where to point the profiler.

If you don't have long-running metrics yet, get them before doing anything else (see Phase 2). Profiling without this context means you don't know if you're chasing a real leak or normal GC behavior.

## Phase 1: Understand what you're actually measuring

`process.memoryUsage()` returns:

```js
{
  rss: 123456789,        // Resident Set Size — total memory held by the process (JS heap + native/C++ memory + code + stack)
  heapTotal: 50000000,   // memory V8 has currently allocated for the JS heap
  heapUsed: 30000000,    // memory actually in use within that heap right now
  external: 2000000,     // memory used by C++ objects bound to JS objects (e.g. Buffers pre-Node 8 behavior, some native bindings)
  arrayBuffers: 500000   // memory allocated for ArrayBuffers/Buffers (subset of external in modern Node)
}
```

Why this matters: **the leak can be inside the V8 JS heap, or outside it.**

- If `heapUsed`/`heapTotal` climb → the leak is JS objects being retained by references somewhere (closures, arrays, caches, listeners). This is the common case, and Chrome DevTools heap snapshots will show it directly.
- If `heapUsed` stays flat but `rss` and/or `external`/`arrayBuffers` climb → the leak is likely in native memory: unreleased Buffers, a native addon, unclosed file descriptors/sockets, a database driver leaking connections/cursors, or an image/crypto library holding native memory. Heap snapshots of the JS heap won't show this directly — you need OS-level tools (`lsof`, `/proc/<pid>/status`, native leak detection) instead.

This split is the single most important diagnostic branch — figure out which side of the wall the leak is on before choosing your tools.

A second subtlety: **V8 doesn't collect eagerly.** `heapUsed` climbing over a short window can just mean GC hasn't run yet, not that memory is unreachable. To check for real, force a GC and see if the number comes back down:

```bash
node --expose-gc your-server.js
```

```js
if (global.gc) {
  global.gc();
  console.log(process.memoryUsage());
}
```

If heapUsed drops back to baseline after a forced GC, it wasn't a leak, just uncollected garbage waiting its turn. If it stays high after a forced GC, those objects are genuinely still reachable from a GC root — that's your leak.

## Phase 2: Instrument before you investigate

Set this up if it doesn't already exist:

- Periodic logging or metrics export of `process.memoryUsage()` (every 10-30s is plenty), ideally tagged with instance/pod ID and deploy version. `prom-client`'s default metrics collector does this for free if you're on Prometheus/Grafana.
- Event loop lag metric (leaks that cause frequent large GCs show up as event loop lag spikes too — useful corroborating signal).
- Alerting on the *trend* (linear regression slope of heap baseline over N hours), not just an absolute threshold — absolute thresholds catch OOM one hour too late.
- If containerized, capture memory limit vs usage so you can see how close you are to an OOM-kill and correlate kill events with the metric graph.

This instrumentation is what let you do Phase 0, and it's what you'll use in Phase 9 to confirm the fix actually worked in production over time, not just in a 5-minute local test.

---

## Phase 3: Reproduce it on demand

Do not try to hunt a leak live in production first. Get a reliable local/staging reproduction — it's dramatically faster to iterate on, and safe to crash repeatedly.

1. **Isolate the surface.** Using the correlation from Phase 0 (which endpoint/job/feature), hit *only* that code path in isolation if you can. If you don't know yet, you'll bisect by traffic shape (below).
2. **Generate sustained, repetitive load** against the suspect endpoint(s):

   ```bash
   npx autocannon -c 50 -d 120 http://localhost:3000/api/suspect-endpoint
   ```

   or `k6`, `artillery`, or even a plain `for` loop calling the function directly in a script if the leak isn't HTTP-related (e.g., a queue consumer or cron job).

3. **Shrink the heap ceiling** to make the leak manifest faster and crash sooner, so your iteration loop is minutes, not hours:

   ```bash
   node --max-old-space-size=128 your-server.js
   ```

4. **Bisect by feature/route** if you don't know the culprit: disable half your routes/middleware, rerun the load test, see if the leak persists. Binary-search down to the smallest reproducing surface. If the leak was introduced recently, `git bisect` combined with "run load test, check if heap baseline rises" as the bisection script works well:

   ```bash
   git bisect start
   git bisect bad HEAD
   git bisect good <last-known-good-tag>
   git bisect run ./scripts/leak-check.sh   # script runs load test + checks heap growth, exits 0/1
   ```

Once you can trigger meaningful, repeatable growth in under a couple minutes locally, you're ready to profile.

## Phase 4: Capture heap snapshots

You need at least two snapshots — one baseline, one after sustained load — to do a meaningful diff. Three is even better (baseline, mid, late) so you can see the trend rather than a single delta.

### Option A — Chrome DevTools, interactively

```bash
node --inspect your-server.js
# or for an already-running process, send SIGUSR1 to enable inspector on the fly:
kill -USR1 <pid>
```

Open `chrome://inspect` in Chrome, click "Open dedicated DevTools for Node" (or "inspect" under Remote Target), go to the **Memory** tab, select **Heap snapshot**, click **Take snapshot**. Run your load test, then take a second snapshot.

### Option B — Programmatic, triggerable via signal (works well for staging/production)

Using the built-in `v8` module (no dependency needed, Node ≥ 11.13):

```js
const v8 = require('v8');
const fs = require('fs');

process.on('SIGUSR2', () => {
  const filename = `/tmp/${Date.now()}.heapsnapshot`;
  const snapshotStream = v8.getHeapSnapshot();
  const fileStream = fs.createWriteStream(filename);
  snapshotStream.pipe(fileStream).on('finish', () => {
    console.log(`Heap snapshot written to ${filename}`);
  });
});
```

Trigger it with:

```bash
kill -USR2 <pid>
```

Take one snapshot at baseline, run load, take another. Pull both `.heapsnapshot` files down and load them into Chrome DevTools' Memory tab (there's a "Load" button) even though they weren't captured through DevTools directly.

The `heapdump` npm package does the same thing with a slightly older API if you prefer it:

```js
const heapdump = require('heapdump');
process.on('SIGUSR2', () => heapdump.writeSnapshot((err, filename) => console.log('wrote', filename)));
```

### Option C — clinic.js

```bash
npx clinic heapprofiler -- node your-server.js
# run your load test against it, then Ctrl+C
```

This produces an interactive flamegraph-style HTML report of allocations, which is a good complementary view to raw snapshots. `clinic doctor` is also worth running first as a general triage step — it watches CPU/event-loop/memory and tells you which specific clinic tool to reach for next.

**Important caution for production:** taking a heap snapshot is stop-the-world — it pauses the event loop, and for a multi-GB heap this can take several seconds to tens of seconds. Do this on a canary instance or an instance you've drained from the load balancer, not one actively serving user traffic, if at all possible.

## Phase 5: Analyze the snapshots (the core skill)

Load both snapshots into Chrome DevTools' Memory panel (left sidebar will list each snapshot you took/loaded).

1. Select the **later** snapshot, then switch the view dropdown from "Summary" to **"Comparison"**, and pick the earlier snapshot as the comparison baseline.
2. The Comparison view shows, per constructor/object-type: `# New`, `# Deleted`, `# Delta`, and size deltas. **Sort by `# Delta` or "Size Delta" descending.** This is the single most useful view in the entire process — it directly shows you which object types are accumulating and never getting freed between the two snapshots.
3. Ignore small deltas and V8-internal noise (`(system)`, `(compiled code)`, small deltas in `string`). Focus on:
   - Your own application's class/constructor names growing steadily
   - `(closure)` growing — suggests closures are being created and retained (timers, listeners, promise chains)
   - `Array`/`(array)` growing — suggests an unbounded array/queue/buffer
   - `Object` growing — suggests a plain-object cache or map-like structure with no eviction
   - `Map`/`Set` internal storage growing
4. **Click into a growing entry.** In the bottom pane, look at **Retainers** — this shows the chain of references keeping each instance alive, walking up to a GC root (usually something like a global variable, a module-level singleton, an active `Timeout`, or an `EventEmitter`'s internal listener array). This retainer chain is literally the answer to "why isn't this being collected" — follow it up until you recognize your own code.
5. Understand **Shallow Size vs Retained Size**:
   - *Shallow size*: memory used by the object itself only.
   - *Retained size*: memory that would be freed if this object (and everything exclusively reachable through it) were garbage collected.
   - Sort by retained size to find the objects whose removal would free the most memory — these are your highest-value targets, even if their shallow size looks small.
6. A useful trick: right after taking a snapshot in DevTools, you can click "Collect garbage" (the trash-can icon) to force GC immediately before snapshotting, which removes noise from objects that were merely pending collection.

Do this comparison across your baseline→mid and mid→late snapshots. Objects that keep showing up as `# New` with very few or zero `# Deleted` across *multiple* comparisons, and whose count keeps climbing in proportion to requests served, are your leak.

## Phase 6: Recognize the usual suspects

Once you've identified *what* object type is piling up, here's the catalog of causes to check against, roughly in order of how often they show up in real Node services:

### 1. Unbounded module-level cache
```js
// BAD
const responseCache = {};
app.get('/data/:id', async (req, res) => {
  const id = req.params.id;
  if (!responseCache[id]) responseCache[id] = await fetchExpensiveData(id);
  res.json(responseCache[id]);
});
```
```js
// FIX — bounded, with eviction
const { LRUCache } = require('lru-cache');
const responseCache = new LRUCache({ max: 500, ttl: 1000 * 60 * 5 });

app.get('/data/:id', async (req, res) => {
  const id = req.params.id;
  let data = responseCache.get(id);
  if (!data) { data = await fetchExpensiveData(id); responseCache.set(id, data); }
  res.json(data);
});
```

### 2. Event listener accumulation
```js
// BAD — adds a new listener on every connection, never removed
function handleConnection(socket) {
  eventBus.on('broadcast', (msg) => socket.send(msg));
}
```
```js
// FIX
function handleConnection(socket) {
  const onBroadcast = (msg) => socket.send(msg);
  eventBus.on('broadcast', onBroadcast);
  socket.on('close', () => eventBus.off('broadcast', onBroadcast));
}
```
Node gives you a free early-warning signal here: `MaxListenersExceededWarning: Possible EventEmitter memory leak detected`. **Don't just raise the limit or suppress this warning — it's telling you exactly what to go investigate.**

### 3. Timers that are never cleared
`setInterval`/recursive `setTimeout` chains left running, especially ones whose closures capture large objects (a full `req`, a big buffer, an accumulating array). Always store the handle and clear it in the relevant cleanup/shutdown path; use `.unref()` on timers that shouldn't keep the process alive.

### 4. Closures over more than they need
```js
// BAD — keeps the entire (possibly huge) req.body alive for 60s just to log one field
app.post('/report', (req, res) => {
  const bigPayload = req.body;
  setTimeout(() => console.log(bigPayload.id), 60000);
});
```
```js
// FIX — extract only the primitive you need before creating the closure
app.post('/report', (req, res) => {
  const id = req.body.id;
  setTimeout(() => console.log(id), 60000);
});
```

### 5. Unbounded arrays/queues without backpressure
Buffering incoming items (log lines, jobs, socket messages) into an in-memory array while the consumer is slow or stalled, with no cap. Fix: respect stream backpressure (check the boolean return of `.write()`, use `pause()`/`resume()`), cap queue length, or push overflow to an external queue (Redis/SQS) instead of holding it in process memory.

### 6. Streams/sockets not destroyed on error paths
Forgetting `.destroy()` on error, not unpiping, leaving listeners attached to a stream that's otherwise done. Leaks both JS-side listener references and native file descriptors.

### 7. In-flight promise maps never cleaned up
```js
// BAD — entries added for de-dupe, but only deleted on the success path
const inFlight = new Map();
async function getOrFetch(key) {
  if (inFlight.has(key)) return inFlight.get(key);
  const p = fetchThing(key).then(result => { inFlight.delete(key); return result; });
  inFlight.set(key, p);
  return p;
}
```
If `fetchThing` rejects, the entry is never deleted and that promise (plus its closure) is retained forever. Fix: delete in a `finally`, not just on the success branch.

### 8. Misconception to rule out: circular references
V8 uses a mark-and-sweep/tracing collector, **not** reference counting — a cycle of plain JS objects with no path from a GC root is collected normally. If you find a cycle in a snapshot and assume that's "the leak," keep looking: something else (a global, a listener, a timer, a closure held by a native handle) must be anchoring that cycle to a root, or it wouldn't have survived to appear in the snapshot at all. The retainer chain (Phase 5, step 4) will show you that anchor.

### 9. `Map`/`Set` used where `WeakMap`/`WeakSet` belongs
```js
// BAD — regular Map holds a strong reference to `req` forever
const metadata = new Map();
app.use((req, res, next) => { metadata.set(req, { startTime: Date.now() }); next(); });
```
```js
// FIX
const metadata = new WeakMap();
app.use((req, res, next) => { metadata.set(req, { startTime: Date.now() }); next(); });
```
With a `WeakMap`, once `req` itself is otherwise unreachable, the entry (and whatever it points to) can be collected. With a regular `Map`, `req` — and its entire retained subgraph — lives forever.

### 10. Native / off-heap leaks
If Phase 1 pointed you at `external`/`arrayBuffers`/`rss` growing while `heapUsed` stays flat: check native addons, `Buffer.allocUnsafe` misuse, image/crypto/compression libraries, and especially **database driver connection or cursor leaks** (a pooled client not released in a `finally`, an open cursor never closed). Also check file-descriptor count over time as a proxy:
```bash
watch -n5 'lsof -p <pid> | wc -l'
```
A steadily climbing FD count means sockets/files aren't being closed, which usually drags native buffers along with them.

### 11. Logging/tracing/APM middleware retaining requests
Debug middleware that pushes `req`/`res` (or large slices of them) into an array "for later inspection," or a tracing shim that never finalizes/evicts old spans. Easy to miss because it looks like observability code, not business logic.

## Phase 7: Pinpoint the exact allocation site

Once you know *what* is leaking (Phase 5/6) but need to know precisely *where in the code* it's allocated, use Chrome DevTools' **Allocation instrumentation on timeline** (in the Memory tab dropdown, next to Heap Snapshot). Start recording, run your load test, stop recording. Bars that stay **blue** (rather than fading to grey) represent allocations that survived and are still retained — click one and you get the actual JS stack trace of the allocation, which usually takes you directly to the offending line.

Other tools worth knowing about for this phase:

- `node --trace-gc your-server.js` — prints every GC event with heap-before/heap-after. Frequent full ("Mark-sweep") GCs that barely reduce heap size is a strong leak signature, visible even without a snapshot.
- `node --prof your-server.js` + `node --prof-process isolate-*.log > processed.txt` — V8-level profiling log, more CPU-oriented but useful for correlating GC overhead with specific code.
- `v8.getHeapStatistics()` / `v8.getHeapSpaceStatistics()` — programmatic breakdown by heap space (new space, old space, large object space, code space, map space) if you want to graph this without full snapshots.
- APM tools (Datadog, New Relic, Dynatrace) increasingly ship built-in Node heap profiling — if you already have one integrated, check there before reaching for raw tooling.

---

## Phase 8: Fix it

Apply the fix that matches the pattern you found in Phase 6. A few general principles regardless of pattern:

- Prefer bounding things (cache size, queue length, TTL) over trying to track every reference perfectly by hand.
- Anywhere you `.on()`, ask "what removes this listener, and when?" If you can't answer that in one sentence, that's the bug.
- Anywhere you create a `setInterval`/recursive `setTimeout`, ask the same question about `clearInterval`/breaking the recursion.
- Prefer `WeakMap`/`WeakSet` for metadata keyed by objects you don't otherwise control the lifetime of.
- Always release pooled resources (DB connections, workers) in a `finally`, not just the happy path.

---

## Phase 9: Verify the fix

Don't trust a fix until you've re-proven it under the same conditions that revealed the leak:

1. Re-run the exact load test from Phase 3 against the fixed code.
2. Take new baseline/late snapshots and re-run the Comparison view — the object type that was growing should now show roughly `# New` ≈ `# Deleted` (flat, not accumulating).
3. Run a **soak test**: extended duration (many hours, ideally overnight) at realistic/production-like traffic in staging, watching the heap-baseline metric from Phase 2. A 2-minute load test can miss slow leaks (e.g., one leaked object per 10,000 requests); a multi-hour soak won't.
4. Only after the soak test shows a flat baseline should this go to production — and even then, watch the Phase 2 dashboards closely for the first day or two after deploy.

---

## Phase 10: Prevent recurrence

- Keep the heap-baseline-trend alerting from Phase 2 running permanently, not just during the incident.
- Treat container/orchestrator restart-on-OOM as a safety net, never a fix — log every time it triggers so a "fixed" leak that regresses doesn't silently hide behind auto-restarts again.
- Add a lightweight regression check for anything that was genuinely leak-prone: a script that exercises the code path N times, forces GC, and asserts heap growth stays under a threshold; run it in CI for that module going forward.
- During code review, specifically ask of any `.on()`, timer, cache, or pooled-resource acquisition: "what removes/clears/releases this, and under what conditions (including error paths)?"
- Periodically re-run soak tests in staging for high-traffic or long-lived services, not just after incidents.

## Quick-reference cheat sheet

| Signal | Likely cause | Where to look |
|---|---|---|
| `heapUsed` flat after forced GC | Not a leak, just pending GC | N/A |
| `heapUsed`/`heapTotal` climb, survive forced GC | JS objects retained by references | Heap snapshot Comparison view |
| `rss`/`external`/`arrayBuffers` climb, `heapUsed` flat | Native memory / buffers / FDs | `lsof`, native addons, DB driver, Buffer usage |
| `MaxListenersExceededWarning` | Listener leak | Every `.on()` without matching `.off()` |
| Frequent full GCs, heap barely shrinks | Something anchored at a GC root | `--trace-gc`, retainer chain in snapshot |
| Growth proportional to request count, never per-connection cleanup | Per-request closure/listener/cache leak | Allocation timeline, retainers |
| OOM kills at roughly fixed uptime regardless of load | Slow steady leak | Long-window baseline graph, soak test |

That's the complete process end to end: confirm it's real, understand what you're measuring, instrument, get a fast local reproduction, capture snapshots correctly, use the Comparison + Retainers views to find what's growing and why it's rooted, match it against the common patterns, pinpoint the exact allocation site if needed, fix, verify with both a targeted re-test and a long soak, then lock in monitoring so it can't silently come back.
