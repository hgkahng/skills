`git merge` combines two branches by creating a new merge commit that ties together both histories, while `git rebase` rewrites your branch's commits so they appear as if built directly on top of the target branch, producing a linear history with no merge commit.

Merge is non-destructive: existing commits are untouched, and the merge commit records exactly how and when the branches diverged and joined. This preserves true history but can leave a cluttered commit graph with frequent merges.

Rebase replays your commits one by one onto the new base, generating entirely new commits with new SHAs. The result is a clean, linear log that's easier to read, but it rewrites history — which is dangerous on branches others have already pulled, since their local history diverges from the rewritten one.

Common convention: use rebase to keep local/feature branches tidy before merging (`git pull --rebase`, or rebasing a feature branch onto `main` before opening a PR), and use merge when integrating completed work into a shared branch like `main`, where preserving true history matters and rewriting is unsafe.
